# UI表示規約

**システム名：** Nexus（国内SES向け 人材・案件マッチングシステム）
**位置づけ：** 画面をまたいで一貫させるべき「表示の原子」と「ラベルの出し分け」を定める横断規約。個々の部品の Props は `コンポーネント設計書.md`、画面ごとの要件は `画面一覧・遷移図.md` を参照する。

> **【2026-08-17 確定】本書を新規作成（issue #57）**
> **背景：** 同じ条件（単価・開始時期・勤務形態・欠損表現）が、人材一覧・案件一覧・マッチング結果で別々の実装・別々の語彙で表示されていた。単価の書式は3実装、日付ラベルの生成は3リソースにコピペ、欠損は「未設定/未定」「省略」「—」の3通りに分岐していた。ワイヤーフレーム（WF_03 / WF_06 / WF_09）自体も画面間で不統一で、WF 準拠だけでは決着しなかった。
> **理由：** 表示の一貫性は個々の画面設計では担保できず、横断の拠り所が要る。機能設計（データモデル・画面・API）に対して**非機能・横断の方針を集約する場所が無い**ことが指摘されていた（issue #43-45）ため、まず表示規約を1枚として独立させた。並行制御・トランザクション・エラーハンドリングを含む方式設計書が作られた際は、本書をその一章として参照・吸収してよい。

---

## 1. 基本原則：原子は統一し、合成は画面に委ねる

| 区分 | 内容 | 扱い |
|---|---|---|
| **原子** | 値そのものの表現（単価の書式・日付ラベル・欠損の語彙・値/カテゴリの描画） | **必ず統一**。共通プリミティブ1箇所に実装を集約する |
| **合成** | 配置・密度・どのブロックに置くか | **画面の主役に応じて可変**。マッチング結果はスコアが主役なので条件を1行に圧縮し、一覧は条件が主役なのでラベル付きで並べる、といった差は許容する |

ただし「ラベルを出すか出さないか」は無基準にせず、後述の**3つの型**のいずれかを選ぶ。

---

## 2. ラベルの出し分け（3つの型）

**大原則1：項目名は必ず1回だけ出す。**（0回＝何の値か分からない、2回＝「単価｜単価未定」のような重複、どちらも作らない）
**大原則2：ラベルの要否は項目ごとに決めず、ブロックが属する型で決まる。1ブロック＝1型、混在させない。**

### 型1：ラベル列（key-value）

固定幅のラベル列＋値。**全項目にラベルを出す**。

- 適用：詳細画面の項目表（`density="detail"`）、一覧カードの条件ブロック（`density="card"`）
- 実装：`Components/Common/FieldRow`
- **値側の欠損トークンは項目名を含めない**（「単価」ラベルの右は「未定」であって「単価未定」ではない）

### 型2：圧縮メタ行

`｜` 区切りで多項目を1行に畳む。**ラベル語は視覚的に出さない**。

- 適用：見出し（氏名・案件名）直下のメタ行すべて（人材一覧カード・案件一覧カード・マッチング結果カード・マッチングサマリー）
- 実装：`Components/Common/MetaRow` ＋ `MetaItem`
- 値は単位・書式で自己識別させる（`60万円〜80万円` / `2026/08/01〜` / `3名` / `常駐`）
- **項目名は捨てず `sr-only` で支援技術に渡す**（`MetaItem` の責務）。視覚的に消しても情報は落とさない
  - ただし**欠損トークン（「クライアント未設定」）は値に項目名を含む**ため、`MetaItem` はその場合 `sr-only` を出さない（「クライアント：クライアント未設定」と二重に読まれるのを防ぐ）
- アイコンは視覚的なスキャン補助として使い、`aria-hidden` を付ける。**項目名の担保をアイコンに委ねない**
- **欠損時のみ項目名入りトークンを出す**（「単価未定」「クライアント未設定」）。値が無いときこそ何の項目か分からなくなるため
- **値が無くてもセグメントごと消さない**（消すと「値が無い」のか「読み落とした」のか区別できない）
  - 例外：**詳細画面の見出し直下サマリー**は、同じ画面の下部に全項目の項目表（型1）が必ず出るため、**値がある項目のみを出す**（同一画面での重複を避けるため）。サマリー内で「消える項目」と「未定と出る項目」が混在しないようにする。一覧カード・マッチング結果にはこの例外を適用しない（そちらは必ず欠損トークンを出す）

#### 詳細画面サマリーの構成（マッチングサマリーに準拠）

```
氏名／案件名（2xl bold）  [ステータスバッジ]
（人材のみ）カナ
属性メタ（型2・｜区切り）  │  担当／サブ（型3）
```

- **バッジはステータスだけ**にし、見出しの右に置く。稼働可能時期・参画開始時期・募集人数などをピルで並べない（項目ごとに枠線・背景が変わり、同じ属性がテキストとピルの2表現になるため）。
- それ以外の属性は型2 のメタ行にテキストで並べる。時期・人数など**アイコンが有効な項目は `MetaItem` の `icon` を使う**（項目名は `sr-only`）。

#### バッジ／ピルを使う場所

| 画面 | 使う？ | 理由 |
|---|---|---|
| 一覧カード（人材・案件） | **使う**（ステータス／稼働可能時期／面談回数／募集人数） | 同じ属性を何枚ものカードで**見比べる**場。バッジは位置と形が固定され、値の長さでずれるテキストより比較しやすい |
| マッチング結果カード | 使わない（ステータス相当のマーカーを除く） | スコアが主役で、条件は1行に圧縮するのが目的 |
| 詳細画面サマリー | ステータスのみ | 1件しか出ないため比較の必要がなく、属性ごとにピルを並べると装飾過多になる |

#### 担当者（割当）の表示

- **一覧カード**：短縮名バッジ（`UserAvatar`。先頭4文字＋`…`）＋「担当」ラベル。氏名テキストは幅が可変でカード間の比較を妨げるため圧縮し、全文はホバーのツールチップと `sr-only` で担保する。4文字は**社内ユーザー（日本語名）が対象という前提**で決めた値
- **詳細サマリー・詳細の項目表**：氏名をテキストで表示（`担当：山田太郎 ／ サブ：佐藤花子`）。1件しか出ないため圧縮の必要がない
- **アバターは氏名の代わりであって項目名の代わりではない**。型3（同型の人名が2つ並ぶ）なので「担当」ラベルは必ず併記する
- 担当・サブは**主が先・副が後の対**として並べ、可視ラベルは対に対して1つだけ置く（それぞれの役割は `sr-only` と並び順が担う）

同じ属性がテキストとピルの2表現になること自体は許容する（**合成＝画面の主役に応じた可変**の範囲）。ただし**原子（語彙・書式・濃淡・アイコンの扱い）はどの表現でも同じ**にする。

### 型3：インライン label-value

`担当：山田太郎` のように値の直前に項目名を置く。**同型の値が複数並び、値だけでは対応が取れない場合に限る**。

- 適用：`担当：` / `サブ：`（同型の人名が2つ）、`更新：` / `次回：`（同型の日付が複数）
- **1つのブロックに複数組を横並びにしない**（どの値がどのラベルに対応するか読み取りづらくなる）
  - ただし `担当：山田太郎 ／ サブ：佐藤花子` のように**同一項目の主・副を表す対**は、切り離すと対応が分からなくなるため1組として扱い、横並びを許容する（`更新：` / `次回：` も同様）
- 欠損トークンは項目名を含めない（`サブ：未割当`、`次回：未設定`）

## 3. 欠損値の語彙

実装は `resources/js/lib/emptyValue.ts`（語彙）と `Components/Common/EmptyValue`（表示）が SSOT。**新しい語や項目を足すときは必ず `emptyValue.ts` を更新する**。

### 表示スタイル

**欠損トークンは常に淡色（`text-muted-foreground`）で表示する。** 実値と同じ濃さだと、値が入っているように読めてしまうため。

色は呼び出し側ではなく **`EmptyValue` コンポーネントが持つ**。語彙だけを共通化して色を呼び出し側に委ねていた時期は、同じ「未設定」が濃色・淡色で混在した（例：人材詳細で「最寄駅／路線＝濃色」「経験スキル＝淡色」）。

- React ノードを置ける場所（ラベル列・カードの条件ブロック）→ **`<EmptyValue field="rate" />`**
- 文字列が必要な場所（`TruncatedText` の `text`、テンプレートリテラル、行全体が淡色の圧縮メタ行）→ `emptyText()` を直接使ってよい
- サーバが返す表示ラベル（`available_label` / `start_label`）は null のとき文字列 `"未定"` を返すため、**値の有無（`available_from` / `start_date`）で分岐して `EmptyValue` を描く**。ラベルをそのまま出すと欠損だけ濃色になる

| 語 | 意味 | 対象項目 |
|---|---|---|
| **未設定** | 登録時に入っているはずの情報が空 | 年齢・最寄駅・路線・クライアント・商流・スキル・希望単価・次回アクション日・顧客折衝経験・アピールポイント・特記事項・業務内容詳細・稼働環境・精算幅・勤務地・NG理由・終了日 |
| **未定** | 後から決まり得る条件 | 稼働可能時期・参画開始時期・単価（案件）・募集人数・面談回数・勤務形態 |
| **未割当** | 割当の有無を表す | サブ担当 |
| **未算出** | 入力漏れではなく、まだ計算されていない | マッチスコア |

### 記号（`—` / `-`）を使わない理由

密なデータ表では記号のプレースホルダが一般的で、実際に多くの設計システムがそれを推奨している（例：Cloudscape は空値にハイフンを使うと明記）。本システムは**あえてそれを採らない**。

1. **埋めるべき情報だから。** 単価・開始時期・クライアントは営業担当がこれから入力する項目であり、「空である」ことが次の行動につながる。記号はそれを単なる欠落として流してしまう。
2. **支援技術に意味が伝わらないから。** `—` はスクリーンリーダーで読み飛ばされたり「ダッシュ」と読まれたりして、値の不在が伝わらない。
3. **一貫性のため。** 「省略」「—」「未設定」の3通りが併存していた状態を1語彙に畳む方が、画面をまたいだ比較がしやすい。

参考：[Cloudscape Key-value pairs](https://cloudscape.design/components/key-value-pairs/) / [Cloudscape Empty states](https://cloudscape.design/patterns/general/empty-states/) / [ServiceNow Horizon Label value inline](https://horizon.servicenow.com/workspace/components/now-label-value-inline)（複数の inline label-value を横並びにしない根拠）

## 4. 値の書式

### 単価（月額）

実装は `Components/Common/Rate`。

| 条件 | 表示 |
|---|---|
| 下限・上限あり | `80万円〜100万円` |
| 下限のみ | `80万円〜` |
| 上限のみ | `〜100万円` |
| レンジ無し・備考あり | 備考をそのまま（自由文のため強調しない） |
| すべて無し | `未定`（型2 では `単価未定`） |

- `variant="strong"`（一覧カード・詳細画面）＝ **数値だけが太字濃色**。単位「万円」と範囲記号「〜」は細字淡色にする（値ではなく補助表現のため。濃淡が交互になると数値が読み取りにくい）。単価だけが見出しと焦点を奪い合わないようにする狙いもある。
- `variant="plain"`（型2 のメタ行）＝ 行全体のトーンに合わせて淡色一律。
- **片側だけのレンジも表示できるようにしておく**（`80万円〜` / `〜100万円`）。ただしデータとしては**フォーム・CSV 取込とも相互必須**で片側レンジは作れないため、これは想定外データに対する防御的表示。
- **レンジと備考は排他**（備考は「スキル見合い」＝レンジを提示できない場合に書く欄）。フォーム・CSV 取込の双方で同時入力を禁止しているため、表示側で両方を並べる必要はない。

### 日付ラベル

| 項目 | 生成元 | 書式 |
|---|---|---|
| 人材の稼働可能時期 | `Engineer::availableLabel` | `2026/08/01〜`、null は `未定` |
| 案件の参画開始時期 | `Project::startLabel` | 同上 |

- **表示ラベルの生成はモデルのアクセサに集約する**。Resource 側で書式を組み立てない（一覧・詳細・マッチングで書式がずれる原因になる）。
- ⚠️ **「未定」の語はサーバ（`Engineer::availableLabel` / `Project::startLabel`）とクライアント（`lib/emptyValue.ts`）の二重定義**になっている。語を変える場合は必ず両方を直すこと（サーバ側は `tests/Unit/ProjectStartLabelTest.php` が固定している）。
- **項目名は正式名称に統一する**：案件の `start_date` は「参画開始時期」（DB設計書・API設計書・CSV ヘッダ・フォーム・マスタ管理の項目名と同じ語）。幅の制約がある一覧カードのラベル列だけ「参画開始」と省略してよいが、別語（旧「稼働開始」）は使わない。人材の `available_from` は「稼働可能時期」。
- ラベルとは別に、生の日付（`available_from` / `start_date`）も返す。型2 が「値の有無」で欠損トークンに切り替えるために必要。

### 値とカテゴリ

- **値**（単価・日付・人数・年齢）＝ テキストで表示する
- **カテゴリ**（勤務形態・スキル・商流）＝ 型1 ではタグ（点線ボーダー等）、型2 ではテキスト。行の密度に合わせてよいが、同一ブロック内では揃える

## 5. 情報の階層（濃淡）

- **濃色（`text-foreground`）**：その画面・その行の主役。氏名／案件名、詳細画面の項目表の値、単価などの数値。
- **淡色（`text-muted-foreground`）**：補助情報。見出し直下のメタ行（年齢・最寄駅・クライアント・商流）、担当／サブ・更新日、単位「万円」・範囲記号「〜」、装飾アイコン、欠損トークン。
- **同じブロック内で濃淡を混在させない**。詳細画面のサマリー行はメタも担当も淡色に揃える（一覧カードは既に両方とも淡色）。

## 6. 画面の地色

**参照＝グレー（`bg-muted/30`）／入力＝白** で分ける。

| 種別 | 画面 | 地色 |
|---|---|---|
| 参照系 | 一覧（人材・案件）・ダッシュボード・マッチング結果・進捗管理・完了タブ・マスタ管理・CSV入出力・**人材詳細・案件詳細** | `bg-muted/30` |
| 入力系 | 人材・案件の登録／編集 | 白（既定） |

- 参照系はカード・テーブルなど**白い要素を面の上に並べる**構成のため、地色をグレーにして要素を浮かせる。詳細画面も `SectionCard` が縦に並ぶので同じ扱い。
- 入力系は白のままにして、フォームに集中させる。
- 濃度は `bg-muted/30` に統一する（かつては `/30` と `/60` が混在していた）。
- 実装：一覧・進捗管理は `-m-6` で `<main>` の padding を打ち消し自前のスクロール領域を持つためそこに指定。詳細は `AuthenticatedLayout` の `mainClassName` で `<main>` に指定する（コンテンツが短くても画面全体がグレーになる）。

> **【2026-08-18 確定】** 従来は一覧・管理系だけがグレーで、詳細・登録・編集は白だった。WF にも docs にも「詳細は白」という規定はなく、実装時の付け忘れによる差だったため、参照／入力の軸で整理し直した。

## 7. 状態の見せ方（淡色化のルール）

- **状態そのものはバッジで示す**（`StatusBadge`：募集中／終了／ペンディング、提案可／面談中／提案不可）。
- **カード全体の淡色化は「そのカード上のアクションが実行できない」ことを示す用途に限る。**
  - 適用する：マッチング結果カードの追加不可（掲載停止・上限到達）＝この画面の主アクションであるパイプライン追加が効かない
  - 適用しない：案件一覧の終了案件（詳細閲覧・編集は行える）、人材一覧の提案不可（マッチングボタンのみ非活性）
- **ホバーの表現は対象の種類で決める。**

| 対象 | ホバー | 理由 |
|---|---|---|
| クリック可能なカード（マッチング結果・進捗管理） | `hover:bg-primary/5` ＋ `hover:border-primary/50` ＋ `hover:shadow-md` | グレーの塗りはカンバン列などグレー地の上で背景と同化するため、色相を変えて示す |
| 押せるコントロール（メニュー項目・ページネーション・タグ） | `hover:bg-muted/50` | 白地の上にあり、中立的なグレーで十分に見える |
| テーブル行（押せない・走査補助） | `hover:bg-muted/30` | 行自体はクリックできないため、押せる感を出さず「今見ている行」を示すにとどめる |

- 状態を淡色でも表すと**同じ意味が2つの手段で表現され、画面ごとに適用有無がぶれる**（実際、案件一覧だけ終了案件を淡色化し、人材一覧の提案不可は淡色化していなかった）。

## 8. ドロワー・オーバーレイの境界

**ドロワーのパネルはコンテンツ領域内に収め、幕（オーバーレイ）は画面全体に敷く。**

| 要素 | 範囲 | 実装 |
|---|---|---|
| パネル（ドロワー本体） | コンテンツ領域内。サイドバーの上に乗せない | `Sheet` を**ページのコンテナへ Portal**（`container`）し、`absolute inset-y-0 right-0` で配置 |
| 幕（オーバーレイ） | 画面全体。サイドバーも薄く覆う | 既定の `fixed inset-0` のまま。濃さは `bg-black/25` |

- **パネルを content 内に留める理由**：ドロワーは「一覧のどの行を見ているか」を保ったまま詳細を開く部品であり、サイドバー（画面遷移の導線）まで覆うと、一時的な詳細表示ではなく別画面へ遷移したように見える。WF_09 / WF_10 もドロワーを `.main-content` 内の `position: absolute` として描いている。
- **幕を画面全体に敷く理由**：ドロワーは modal（フォーカストラップ＋外側の操作不可）として開く。幕を content 内に留めるとサイドバーだけが明るいまま押せない状態になり、見た目と操作可否が食い違う。暗くすることで「今は操作できない」ことを示す。
- **濃さは `bg-black/25`**。背後のカード一覧が読める濃度にする（詳細を見ながら一覧の文脈を保つため）。確認ダイアログ（`ConfirmDialog`）の明色ブラー（`bg-white/70 backdrop-blur-sm`）とは目的が異なるので揃えない。ブラーは背後を「一時的に遮る」ための表現で、ドロワーは背後を「読み続けられる」ことが要件。
- `Sheet` の既定値（`fixed` / `bg-black/80` / `p-6`）そのものは変更せず、呼び出し側から `container` / `overlayClassName` / `className` でオプトインする。

> **【2026-08-21 確定】ドロワーを shadcn `Sheet`（Radix Dialog）へ統一（issue #41）**
> **背景：** マッチング結果と進捗管理の2ドロワーが自前のオーバーレイ＋固定パネルで実装されており、フォーカストラップ・ESC・背景スクロールロック・`aria-modal` が無かった。さらにマッチング側は `fixed inset-0` で描画されており、WF_09 に反してサイドバーごと覆っていた（進捗管理側は `absolute` で WF どおり）。
> **理由：** a11y は Radix Dialog に委ねるのが確実だが、素直に移行すると Portal 先が `body` になりパネルがサイドバーを覆う。そこで Portal 先をページのコンテナに指定してパネルだけを content 内に収め、幕は modal の境界を示すため画面全体に残した。**幕の範囲だけは WF（`.main-content` 内）から意図的に逸脱している**が、WF が守ろうとしている「パネルがサイドバーを覆わない」「背後のカードが見える」は維持される。

## 9. アクセシビリティの最低ライン

- 型2 の各項目は `sr-only` の項目名を持つ（`MetaItem` が自動で付ける）
- 装飾アイコン・区切り記号（`｜`）は `aria-hidden`
- **装飾アイコン（Clock / Users 等）は淡色（`text-muted-foreground`）**。値より従属させ、スキャン補助に留めるため。ピル・バッジの中でも同じ（値だけが濃色）
- 項目名を `aria-label` で非対話要素に付けない（支援技術によって無視されるため）。**可視テキストを `sr-only` で隠す方式に統一する**
