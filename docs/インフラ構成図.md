# インフラ構成図（EC2単体構成）

**システム名：** Nexus（国内SES向け 人材・案件マッチングシステム）  
**対象環境：** 研修用途  
**作成日：** 2026-06-10  
**最終更新：** 2026-08-31  
**構成方針：** EC2 1台 + docker-compose によるシンプル構成（HTTPS対応：Nginx + Let's Encrypt）

> **【2026-08-23 修正】laravel コンテナのポートを 8000 → 80 に訂正し、「リリース前チェックリスト（本番）」を新設した。**
> **背景：** リバースプロキシ配下で HTTPS が認識されず Mixed Content が発生した対応（#89）の過程で、本書の記載が実態とずれていることが分かった。本番イメージ（`laravel/Dockerfile`）は Nginx + php-fpm 構成で `EXPOSE 80` しており、`:8000` は開発用 `docker-compose.yml`（`php artisan serve`）のポートだった。また、本番固有の設定注意（`APP_URL` / `TRUSTED_HOSTS` / `SESSION_SECURE_COOKIE` / ポート公開範囲 / ACME の認証方式）が `docs/環境構築手順書.md` の「初期ログイン情報」の中に紛れており、開発環境の構築手順を読む人には不要で、リリース担当者には見つけにくい状態だった。
> **理由：** これらはいずれも**環境の構成そのものに依存する事項**で、アプリのコードを読んでも判断できない。構成を定義している本書に集約し、`docs/環境構築手順書.md` からはリンクのみを張る形にした。

> **【2026-08-23 追記】本番構成がリポジトリ管理外であることを明記し、ロック解除手順（チェックリスト 6）と ACME の `standalone` の扱いを追加した。**
> **背景：** PR #89 のレビューで、本書が前提にする本番 compose と前段 Nginx の設定がリポジトリのどこにも存在せず、読み手が開発用 `docker-compose.yml` と食い違いを起こすことが指摘された。あわせて、ログインのアカウント単位レート制限に**解除手段が無く外部から管理者を締め出せる**点、`standalone` を `webroot` と同じ症状として書いていた点も指摘された。
> **理由：** 「探しても無い」ことが分からないと現地で時間を溶かすため所在を明示した。ロック解除は障害時にしか使わない手順で、リリース担当者が唯一上から順に読むチェックリストに置かないと見つからない。`standalone` は certbot 自身が :80 で応答するため `trustHosts` の影響を受けず、失敗の原因（ポート競合）も対処も別物であり、同一行に書くと切り分けを誤らせる。

> **【2026-08-31 更新・Issue #90】本番構成をリポジトリ管理下に取り込み、`.env` の反映方式の矛盾を解消し、証明書の自動更新設定を追記した。**
> **背景：** 本番 EC2 を実地調査したところ、(a) 「環境変数（本番用 変更箇所）」の項で `.env` の反映方法が**同じ節の中で「再ビルドが必要」と「再ビルドは不要」の両方を述べており矛盾していた**、(b) ACME の認証方式は実際には `standalone` ＋ nginx 停止 hook で運用できていたが、本書は「nginx がポートを掴んでいるため実行できない」と書いていた、(c) **証明書の自動更新が一度も走っておらず、2026-11-19 に失効する状態だった**、の3点が判明した。
> **あわせて「再デプロイ手順（2回目以降）」を新設した。** 本書には初回構築の手順しかなく、既存の EC2 に変更を反映する手順が無かった。変更の種類（`.env` のみ／nginx 設定のみ／コード・依存）で必要な操作が違うこと、マイグレーションと切り戻しの扱いを明記した。
> **あわせて、初期セットアップ手順 4〜8 を本番構成に合わせて書き直した。** 手順 6 が `docker compose run --rm laravel sh -c "npm install && npm run build"`、手順 7 が `docker compose up -d`、手順 8 が `docker exec -it trainingrepo-laravel-1` と、いずれも **`-f docker-compose.prod.yml -p trainingrepo-prod` が付いておらず開発用構成を指していた**。フロントエンドのビルドは `laravel/Dockerfile` の Stage 1 で行われるため手順 6 自体が不要であり、コンテナ名も本番は `trainingrepo-prod-laravel-1` で一致していなかった。あわせて compose 用 `.env`（`MYSQL_ROOT_PASSWORD`）の作成を手順 5-2 として追加した。
> **理由：** (a) は `.dockerignore` の追加とバインドマウントへの変更で「再起動で反映」に統一し、実装と記述を一致させた。(c) の原因は設定の書き忘れではなく、**`cronie` が未導入で `crond` が存在しなかったこと**である。旧手順 10 の指示どおり `/etc/crontab` に certbot の行は追記されていたが、それを実行するデーモンが無かった。Amazon Linux 2023 の最小構成に cron は含まれないため、**手順に cronie の導入を追加**し、あわせて「書いてある」ことと「効いている」ことを分けて確認する手順（`systemctl is-active crond` と `certbot renew --dry-run`）を必須化した。設定ファイルの存在確認だけでは更新が通る保証にならない。

| コンテナ名 | イメージ | 公開ポート | 用途 | 外部公開 |
|---|---|---|---|---|
| nginx | Nginx | 443 / 80 | SSL終端・リバースプロキシ | ✅ 公開 |

| python | Python 3.12 + FastAPI | 8001（内部のみ） | マッチングエンジン・AI連携 | ❌ 内部通信のみ |

> **Certbot** は docker-compose のサービスではなく、EC2ホスト上に直接インストールして証明書の取得・自動更新を行います。

> **【2026-08-31 更新】本番構成はリポジトリ管理下になりました（Issue #90 対応）。**
>
> | 対象 | 所在 |
> |---|---|
> | 本番用 compose（`nginx` を含む 4 サービス構成） | `docker-compose.prod.yml`（リポジトリ直下） |
> | 前段 Nginx の設定 | `nginx-proxy/default.conf` |
> | laravel コンテナ内の Nginx 設定 | `laravel/docker/nginx/default.conf` |
> | compose の変数（`MYSQL_ROOT_PASSWORD`） | `.env`（リポジトリ直下・**git 管理外**）。雛形は `.env.prod.example` |
>
> リポジトリの `docker-compose.yml` は **開発用**で、サービスは `laravel` / `python` / `mysql` の 3 つのみ（`nginx` は無く、`laravel` は `8000:8000` を publish しています）。本番は `docker-compose.prod.yml` を使い、**開発用と本番用で別物**です。
>
> 起動コマンドは以下のとおりで、プロジェクト名 `trainingrepo-prod` を必ず付けます（省略するとボリューム名が変わり、既存の DB データが見えなくなります）。
>
> ```bash
> docker compose -f docker-compose.prod.yml -p trainingrepo-prod up -d
> ```
>
> `trustProxies(at: '*')` の安全性は「前段 Nginx 以外から laravel に到達できないこと」に依存します。これを担保する compose がバージョン管理下に入ったため、レビューで検証できるようになりました。

> **laravel コンテナの中でも Nginx が動きます。** 本番イメージ（`laravel/Dockerfile`）は Nginx + php-fpm 構成で `EXPOSE 80` しており、前段の nginx コンテナからは `:80` で受けます。開発用 `docker-compose.yml` の `8000:8000` は `php artisan serve` を使う開発専用の設定で、**本番とポート番号が異なる**点に注意してください。
>
> **⚠️ `laravel` の `:80` をホストや外部に publish しないこと。** Laravel は `bootstrap/app.php` の `trustProxies` により、直前の接続元が送る `X-Forwarded-For` / `X-Forwarded-Proto` を信頼します。この信頼は「前段 Nginx 以外から laravel に到達できないこと」を前提に成立します（詳細は「リリース前チェックリスト（本番）」の 2）。

## アクセスフロー

### ブラウザ → アプリ（HTTPS）

```
ユーザーPC（ブラウザ）
    │
    │ HTTPS :443  https://<ドメイン名>
    ▼
EC2（パブリックサブネット）
    │
    ▼
nginx コンテナ（:443）
    │ SSL終端（Let's Encrypt 証明書）
    │ HTTP :80（内部通信）
    │ proxy_set_header で Host / X-Real-IP /
    │ X-Forwarded-For / X-Forwarded-Proto を付与
    ▼
laravel コンテナ（:80）
    │ コンテナ内 Nginx → php-fpm
    ├── Inertia.js + React でページを返す
    └── 内部通信: python コンテナ（:8001）へ
            マッチング・AI処理をリクエスト
```

> **HTTP → HTTPS リダイレクト：** `:80` へのアクセスは Nginx が自動的に `:443` へリダイレクトします。

> **⚠️ Nginx が `proxy_set_header` で明示的にセットしていないヘッダーは、クライアントの送信値がそのまま laravel へ素通しされます。** Laravel 側で信頼するのは上記の 4 つのうち `X-Forwarded-For` / `X-Forwarded-Proto` の 2 つだけで、`X-Forwarded-Host` / `-Prefix` / `-Port` は**意図的に信頼していません**（信頼すると絶対 URL のホスト・パス・ポートを外部から差し替えられるため）。`Host` 自体もクライアント由来のため、`trustHosts` の許可リストで別途検証します。

### Python → AWS Bedrock（AI処理）

```
python コンテナ
    │
    │ HTTPS（boto3 / AWS SDK）
    │ IAMロール認証（APIキー不要）
    ▼
AWS Bedrock
    └── Claude モデル
        ├── マッチングスコアの総合判定（100点満点・A〜Dランク）
        ├── スコア算出理由の生成
        ├── 推薦理由の自動生成
        ├── 不足条件の説明
        └── 職務経歴の要約
```

> **補足：** マッチングスコアはルールベース8項目の配点ではなく、**AIによる総合判定方式**（DB設計書 v1.7 / WF_09 v2.0 確定）。スコアはオンデマンド計算でDB保存しない（QA #45 確定）。パイプライン追加時のみスナップショットとして pipelines テーブルに保持する。

## EC2 起動後の初期セットアップ手順

> **コマンド表記の注意：** Docker Compose v2 のコマンドは `docker compose`（スペース区切り）です。  
> 開発環境の手順書にある `docker-compose`（ハイフン区切り）は v1 の表記のため読み替えてください。

```bash
# 1. Docker・Docker Compose v2 のインストール
sudo yum update -y
sudo yum install -y docker
sudo systemctl start docker
sudo systemctl enable docker
sudo usermod -aG docker ec2-user
# ↑ 反映には再ログインが必要

# Docker Compose v2（プラグイン形式）のインストール
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -SL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64 \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose

# インストール確認
docker compose version

# 2. Certbot（Let's Encrypt）のインストール
sudo yum install -y python3 augeas-libs
sudo python3 -m venv /opt/certbot/
sudo /opt/certbot/bin/pip install --upgrade pip
sudo /opt/certbot/bin/pip install certbot certbot-nginx
sudo ln -s /opt/certbot/bin/certbot /usr/bin/certbot

# 3. リポジトリのクローン
git clone git@github.com:<organization>/TrainingRepo.git
cd TrainingRepo

# 4. MySQLデータ永続化の確認（重要）
# docker-compose.prod.yml の mysql サービスに volumes 定義があることを確認すること。
# 定義がない場合、`docker compose down` でDBデータが全消失する。
#
# 例：
#   mysql:
#     volumes:
#       - mysql-data:/var/lib/mysql
# volumes:
#   mysql-data:

# 5. 環境変数の設定
# 5-1. アプリ用（コンテナにバインドマウントで渡される）
cp laravel/.env.example laravel/.env
cp python/.env.example python/.env
# .env の APP_URL・DBパスワード・Bedrock設定を本番値に変更すること

# 5-1-2. APP_KEY を生成して laravel/.env に設定する
# ※ .env は :ro でマウントされるため、コンテナ内の `php artisan key:generate` は
#    「Permission denied」で失敗します。起動前にホスト側で入れておくこと。
echo "base64:$(openssl rand -base64 32)"
vi laravel/.env                  # 出力を APP_KEY= に貼る

# 5-2. compose 用（docker compose が変数展開に使う。リポジトリ直下）
cp .env.prod.example .env
openssl rand -base64 32          # 生成した値を MYSQL_ROOT_PASSWORD に設定
vi .env
# APP_HOST には laravel/.env の APP_URL のホスト部分を設定する
#   例) APP_URL=https://54-168-196-65.nip.io → APP_HOST=54-168-196-65.nip.io
# ※ 一致していないと laravel の healthcheck が 400 で失敗し続け、
#    nginx が起動しません（下記「healthcheck の Host」参照）
chmod 600 .env
# ※ 未設定のまま起動すると compose がエラーで停止する（既定値は用意していない）

# 6. 全コンテナのビルドと起動
# ※ フロントエンド（React）のビルドは laravel/Dockerfile の Stage 1 で行われるため、
#    別途 npm install / npm run build を実行する必要はありません。
# ※ -f と -p を必ず付けること。省略すると開発用 docker-compose.yml が使われ、
#    ボリューム名も変わって既存の DB データが見えなくなります。
docker compose -f docker-compose.prod.yml -p trainingrepo-prod up -d --build

# 7. 起動確認（healthy になるまで1〜2分かかります）
docker compose -f docker-compose.prod.yml -p trainingrepo-prod ps

# 8. マイグレーション・シード
# ※ APP_KEY は手順 5-1-2 で設定済み。ここで key:generate は実行しません
#   （.env が :ro マウントのため失敗します）。
docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec laravel sh
php artisan migrate --force
php artisan db:seed --force
exit

# 9. SSL証明書の取得（ドメイン取得・DNS設定完了後に実行）
# ※ 事前にドメインのAレコードをElastic IPに向けておくこと
# ※ 本構成の Nginx は docker-compose のコンテナなので --nginx プラグインは使えません。
#    :80 を掴んでいる nginx コンテナを一時停止する standalone 方式で取得します。
sudo certbot certonly --standalone -d <your-domain.com> \
  --pre-hook  "docker compose -f /home/ec2-user/TrainingRepo/docker-compose.prod.yml -p trainingrepo-prod stop nginx" \
  --post-hook "docker compose -f /home/ec2-user/TrainingRepo/docker-compose.prod.yml -p trainingrepo-prod start nginx"
# 対話形式でメールアドレスを入力し、利用規約に同意すると証明書が取得される
# pre-hook / post-hook は /etc/letsencrypt/renewal/<ドメイン>.conf に保存され、
# 以降の renew でも自動的に使われます（更新のたびに nginx が数十秒停止します）

# 10. cron（cronie）を導入する ★これを飛ばすと手順 11 が無意味になる
# Amazon Linux 2023 の最小構成には cron が入っていません。
# /etc/crontab や /etc/cron.daily があっても、実行するデーモンが存在しません。
sudo dnf install -y cronie
sudo systemctl enable --now crond
systemctl is-active crond    # → active であること

# 11. 証明書の自動更新設定（cron）
sudo tee /etc/cron.d/certbot-renew > /dev/null <<'EOF'
# Let's Encrypt 証明書の自動更新（1日2回チェック・期限30日前から更新）
# $((RANDOM)) を使うため SHELL は bash を明示する
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin
# 時刻は UTC。16,18 は JST の 01:00 / 03:00（理由は下記）
# ランダム遅延を入れて ACME サーバーへの集中を避ける
0 16,18 * * * root sleep $((RANDOM \% 3600)) && /opt/certbot/bin/certbot renew -q
EOF
sudo chmod 644 /etc/cron.d/certbot-renew
# 1日2回チェックし、有効期限が30日を切ったら自動更新される
# ⚠️ `\%` のバックスラッシュは必須（cron は素の % を標準入力の区切りとして解釈するため）
# ⚠️ standalone では --deploy-hook を付けないこと（理由は下記）

# 12. 自動更新が実際に通るかを確認（必須）
sudo certbot renew --dry-run
```

> **⚠️ `standalone` 方式では `--deploy-hook` で nginx を reload しないでください。**
>
> certbot のフック実行順は `pre_hook` →（認証・発行）→ `deploy_hook` → `post_hook` です。手順 9 で設定した `pre_hook` は nginx コンテナを **stop** するため、`deploy_hook` の時点でコンテナは停止しており、`docker compose exec nginx nginx -s reload` は失敗します。
>
> **standalone では deploy-hook 自体が不要です。** 更新後に `post_hook` が `start nginx` するため、nginx は起動時に新しい証明書を読み込みます。deploy-hook が要るのは、nginx を止めない **`webroot` 方式に移行した後**だけです（「5. ACME の認証方式」参照）。
>
> なお **`--dry-run` は既定で deploy hook を実行しない**ため、この不整合はドライランでは表面化しません。最初から付けないでおくのが安全です。

> **⚠️ `standalone` 運用では、実行時刻を業務時間帯から外してください。**
>
> 更新が実際に走るとき、pre-hook が nginx コンテナを停止するため **数十秒のダウンタイムが発生します。** cron の時刻は **UTC** で解釈されるため、certbot 公式が例示する `0 0,12 * * *` をそのまま使うと **JST では 09:00 と 21:00**、ランダム遅延込みで **09:00〜10:00 JST** に停止することになります。
>
> 本書では `0 16,18 * * *`（＝ **01:00 / 03:00 JST**、遅延込みで最大 04:00 JST）を採用しています。更新は期限30日前から始まり実質60〜90日に1回ですが、業務時間帯を避ける価値はあります。
>
> **`webroot` 方式へ移行すればダウンタイム自体が無くなる**ため、時刻の調整は移行までの暫定対処です。

> **⚠️ 手順 10（cronie の導入）を飛ばすと、cron の設定は書けても実行されません。**
>
> 2026-08-31 の調査で、本番 EC2 が**まさにこの状態**でした（Issue #90）。`/etc/crontab` には旧手順書のとおり certbot の行が追記されており、ファイルの更新日時も構築時と一致していました。**しかし `cronie` が未導入で `crond` が存在せず、その行を実行するものが無かった**ため、更新が一度も走っていませんでした。
>
> ```console
> $ rpm -q cronie
> package cronie is not installed
> $ ls -ld /etc/cron.d
> ls: cannot access '/etc/cron.d': No such file or directory
> $ tail -1 /etc/crontab
> 0 0,12 * * * root /opt/certbot/bin/python -c '...' && sudo certbot renew -q   ← 書かれてはいる
> ```
>
> **「設定を書き忘れた」のではなく「書いても動かない」ケースです。** `/etc/cron.daily` などのディレクトリは cronie 抜きでも存在するため、cron が動いていると誤認しやすくなっています。エラーもログも出ず、`MAILTO=root` が設定されていても通知は来ません（デーモン自体が無いため）。
>
> 構築後は、**設定を書いたことではなく、実行される状態にあることを確認してください。**
>
> ```bash
> systemctl is-active crond              # active であること
> cat /etc/cron.d/certbot-renew          # ファイルが存在すること
> sudo certbot renew --dry-run           # 「Congratulations, all simulated renewals succeeded」が出ること
> ```
>
> `--dry-run` は pre-hook / post-hook も実行するため、**nginx が短時間停止します。** アクセスの少ない時間帯に実施してください。

## EC2 再起動時の自動起動設定

**`docker-compose.prod.yml`** の各サービスに `restart: always` を設定することで、EC2 再起動後もコンテナが自動で立ち上がります。あわせて MySQL の volumes 定義も確認してください（いずれも設定済みです）。

services:

    restart: always
  laravel:
    restart: always
  python:
    restart: always
  mysql:
    restart: always
    volumes:
      - mysql-data:/var/lib/mysql   # データ永続化（必須）

volumes:
  mysql-data:
```

## 再デプロイ手順（2回目以降）

初期セットアップ済みの EC2 に、`develop` の変更を反映する手順です。**初期セットアップ手順とは別物**なので、こちらを使ってください。

### 1. 何が変わるかを先に確認する

```bash
cd /home/ec2-user/TrainingRepo
git fetch origin
git log --oneline HEAD..origin/develop        # 取り込まれるコミット
git diff --stat HEAD origin/develop           # 変更されるファイル
```

`laravel/Dockerfile`・`python/Dockerfile`・`requirements.txt`・`composer.lock` が含まれていれば**再ビルドが必要**、`docs/` や `.md` だけなら**デプロイ自体が不要**です。

### 2. バックアップ

DB スキーマに変更（`database/migrations/` の差分）がある場合は必須です。

```bash
docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec -T mysql \
  sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction ses_matching' \
  > ~/backup-$(date +%Y%m%d-%H%M).sql
ls -lh ~/backup-*.sql
```

> **⚠️ `sh -c '...'` とシングルクォートは必須です。** `$MYSQL_ROOT_PASSWORD` はコンテナ内の環境変数で、**ホスト側のシェルには存在しません。** シングルクォートで囲まずに書くとホストで空文字に展開され、`-p` だけが渡ってパスワード入力待ちになります。`exec -T` かつリダイレクト中は入力できないため、**バックアップが取れないまま失敗します。**

### 3. 取得

```bash
git pull
git log --oneline -1
```

> ⚠️ `.env` は `.gitignore` 済みのため `git pull` で上書きされません。`.env.prod.example` に新しいキーが増えていないかは確認してください。
>
> ```bash
> diff <(grep -o '^[A-Z_]*=' .env.prod.example | sort) <(grep -o '^[A-Z_]*=' .env | sort)
> ```

### 4. 反映

**変更の種類によって必要な操作が異なります。**

| 変更内容 | 操作 |
|---|---|
| `.env` のみ | `docker compose -f docker-compose.prod.yml -p trainingrepo-prod restart laravel` |
| `nginx-proxy/default.conf` のみ | **下記の `nginx -t` を通してから** `docker compose -f docker-compose.prod.yml -p trainingrepo-prod restart nginx` |
| アプリのコード・依存・Dockerfile | 下記の再ビルド |

```bash
docker compose -f docker-compose.prod.yml -p trainingrepo-prod up -d --build
```

特定のサービスだけ入れ替える場合はサービス名を付けます（例：`... up -d --build python`）。

> **⚠️ nginx の設定を変えたときは、再起動の前に必ず構文検証を通してください。** 前段 nginx が起動に失敗するとサイト全体が停止します。
>
> ```bash
> # 稼働中のコンテナで、新しい設定ファイルを検証する
> docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec nginx nginx -t
> ```
>
> `test is successful` を確認してから `restart nginx` します。設定はバインドマウントなので、コンテナ内には既に新しい内容が見えています。
>
> `restart` ではなく `reload` で済む変更（証明書の差し替えなど）なら、無停止で反映できます。
>
> ```bash
> docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec nginx nginx -s reload
> ```

### 5. マイグレーション

`database/migrations/` に差分があった場合のみ実行します。

```bash
docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec laravel php artisan migrate --force
```

> `--force` は本番環境（`APP_ENV=production`）での確認プロンプトを飛ばすために必要です。**2 のバックアップを取ってから実行してください。**

### 6. 動作確認

```bash

## リリース前チェックリスト（本番）

> 対象：本番・ステージングへリリースする担当者
> `.env` は git 管理外のため、設定漏れはコードレビューでも CI でも検出されません。リリースのたびに上から順に確認してください。

| # | 確認項目 | 漏らしたときに起きること |
|---|---|---|
| 1 | `ALLOWED_EMAIL_DOMAINS` が設定されている | 任意ドメインのメールでユーザー登録できてしまう |
| 2 | `laravel` コンテナの `:80` を外部公開していない | 転送ヘッダーの偽装でレート制限を回避される |
| 3 | `SESSION_SECURE_COOKIE=false` が本番 `.env` に無い | HTTPS でもセッションクッキーに `Secure` が付かない |
| 4 | `APP_URL` が実際の公開ホストと一致している | **全リクエストが 400 になる** |
| 5 | ACME（Let's Encrypt）の認証方式を把握している | ホスト名変更時に証明書の取得・更新が失敗する |
| 6 | ログインがロックされたときの解除手順を把握している | 管理者が締め出されたまま最大15分復旧できない |
| 7 | **`crond` が動いており、`--dry-run` が通る** | **90日後に証明書が失効し、HTTPS が全面停止する** |
| 8 | `MYSQL_ROOT_PASSWORD` 等の秘匿値が compose ファイルに直書きされていない | リポジトリに認証情報が残る |

### 1. `ALLOWED_EMAIL_DOMAINS` を必ず設定すること

ユーザーのメールアドレス（＝ログインID）に許可する社内ドメインを `laravel/.env` にカンマ区切りで設定します（例：`ALLOWED_EMAIL_DOMAINS=example.co.jp,example.com`）。

**未設定のまま本番稼働すると、ドメイン制限が完全に無効化され（形式チェックのみ）、任意ドメインのメールでユーザー登録できてしまいます。** 初期管理者を作成する前に確認してください（作成手順は `docs/環境構築手順書.md` の「12. 初期ログイン情報」）。

### 2. `laravel` コンテナのポートを外部公開しないこと

Laravel は `bootstrap/app.php` の `trustProxies` により、**直前の接続元**が送る `X-Forwarded-For` / `X-Forwarded-Proto` を信頼します。

**この信頼は「前段 Nginx 以外から `laravel` に到達できないこと」を前提に成立します。** compose で `laravel` の `ports:` を publish したり、セキュリティグループで当該ポートを開放すると、クライアントが `X-Forwarded-For` を偽装して直接アクセスでき、**ログイン試行のレート制限（メールアドレス＋IP で 5 回 / 分）を回避できてしまいます。**

本番の compose では `laravel` の `ports:` を定義せず、nginx コンテナからの内部ネットワーク経由のみ到達可能にしてください。

> なお、送信元 IP を分散されると IP 単位の制限は回避できるため、**メールアドレス単位の制限（10 回 / 15 分）**を第 2 段として重ねています（`LoginRequest::ensureIsNotRateLimited`）。ポート非公開はこの前提を守るためのものですが、それ単独に依存する設計にはしていません。

### 3. 本番 `.env` に `SESSION_SECURE_COOKIE=false` が無いこと

理由は「環境変数（本番用 変更箇所）」の注記のとおりです。**`laravel/.env.example` を更新しても、既存の本番 `.env` は直りません。** 実物を開いて確認してください。

```bash
# 本番の .env に false が書かれていないこと（何も出力されなければ OK）
grep -n 'SESSION_SECURE_COOKIE' laravel/.env
```

### 4. `APP_URL` が実際の公開ホストと一致していること

`bootstrap/app.php` の `trustHosts` により、**許可リストに無いホスト名を名乗るリクエストは 400 Bad Request で拒否**されます（Host ヘッダーを偽装して絶対 URL のホストを乗っ取る攻撃を防ぐため）。

許可されるホストは次の 2 つを足したものです。

| 由来 | 内容 |
|---|---|
| `APP_URL` | そのホスト名 1 件（常に許可） |
| `TRUSTED_HOSTS` | カンマ区切りの追加ホスト（任意・既定は空） |

**`APP_URL` が実際の公開ホストとずれると全リクエストが 400 になります。**

`TRUSTED_HOSTS` は「一時的にもう 1 ホスト通したい」ときのための追加枠です（ホスト移行中・監視の IP 直打ちなど）。恒久設定ではないので、用が済んだら空に戻してください。

> **⚠️ `TRUSTED_HOSTS` に書けるのは「ホスト名のみ」です。** 次の書き方は**エラーにならないまま一致せず**、「許可したつもりなのに 400 が返り続ける」形になります（値は正規表現エスケープされるため、安全側に倒れる代わりに誤設定が無言になります）。
>
> | 書いた値 | 実際の挙動 |
> |---|---|
> | `*.example.com` | ワイルドカードは展開されず、どのホストにも一致しない |
> | `new.example.com:8443` | ホスト照合はポートを含まないため一致しない |
> | `https://new.example.com` | スキームを含むと一致しない（`APP_URL` とは書式が違う） |
>
> 正しい書き方：`TRUSTED_HOSTS=new.example.com,10.0.1.20`（対象ホストを 1 件ずつカンマ区切りで列挙）

#### ホスト名（ドメイン / IP）を変更する手順

⚠️ **手順 2 で新ホストを先に許可しておくのが要点です。** 先に DNS と証明書だけ切り替えると、新ホスト宛のリクエストが `APP_URL` 更新まで 400 になり、切り替え作業中にサービスが停止します。

1. DNS レコード / Elastic IP を変更する
2. **`laravel/.env` の `TRUSTED_HOSTS` に新ホスト名を追加し、反映する**（この時点で新旧の 2 ホストが通る状態になります）
   - 例：`TRUSTED_HOSTS=new.example.com`
3. `certbot` で新しいホスト名の証明書を再取得する
   - ⚠️ 認証方式によっては、手順 2 を飛ばすとここで失敗します（後述「5. ACME の認証方式」）
4. **nginx コンテナの `server_name` と `ssl_certificate` / `ssl_certificate_key` のパスを新しいホスト名に更新し、reload する**（証明書は `/etc/letsencrypt/live/<ホスト名>/` 配下に発行されるため、旧ホスト名のパスのままでは TLS 側が先に壊れます）
5. **`laravel/.env` の `APP_URL` を新しいホスト名に更新する**
   - ⚠️ **`https://` を含む完全な URL で書くこと。** `203-0-113-10.nip.io` のようにスキームを省くと `parse_url()` がホストを取り出せず、**全リクエストが 400 になります**（前後の空白も同様）。正：`APP_URL=https://203-0-113-10.nip.io`
6. **`TRUSTED_HOSTS` を空に戻す**（許可範囲を広げたまま放置しない）
7. **リポジトリ直下の `.env` の `APP_HOST` を新しいホスト名に更新する**
   - ⚠️ **ここを忘れると HTTPS が全面停止します。** laravel の healthcheck はこの値を `Host` ヘッダーに使っており、`APP_URL` とずれると `trustHosts` に 400 で弾かれます。healthcheck が失敗し続けると nginx の `depends_on: condition: service_healthy` が満たされず、**前段 nginx が起動しません。**
   - `APP_URL` の**ホスト部分のみ**を書きます（スキーム無し）。例：`APP_URL=https://new.example.com` → `APP_HOST=new.example.com`
   - 反映には laravel の再起動が必要です（compose の変数なので、正しくは `up -d` で再作成されます）
8. **`.env` の変更は該当コンテナの再起動で反映されます（再ビルド不要）。**

   ```bash
   docker compose -f docker-compose.prod.yml -p trainingrepo-prod restart laravel
   ```

   > **【2026-08-31 更新・Issue #90】** 以前は「イメージに含めている場合は再ビルドが必要」と書いていました。`laravel/Dockerfile` が `COPY . .` で `.env` を焼き込んでいたためです。現在は `.dockerignore` で `.env` をビルドコンテキストから除外し、実行時に `docker-compose.prod.yml` のバインドマウント（`./laravel/.env:/var/www/.env:ro`）で渡しているため、**再ビルドは不要**になりました。python 側も同様です。
   >
   > この変更により、APP_KEY・DB_PASSWORD・AWS の鍵がイメージに残らなくなっています。
9. 設定キャッシュを使っている場合のみ `docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec laravel php artisan config:clear` を実行する（現状の `Dockerfile` / `docker/start.sh` は `config:cache` を実行していないため、通常は不要です）

#### 反映後の確認

```bash
# 全サービスが healthy であること（laravel が unhealthy なら APP_HOST を疑う）
docker compose -f docker-compose.prod.yml -p trainingrepo-prod ps

# 正規ホスト → 200 であること
curl -sS -o /dev/null -w "%{http_code}\n" https://<新ホスト>/login
# 偽装ホスト → 400 であること（ホスト注入が塞がっている証跡）
curl -sS -o /dev/null -w "%{http_code}\n" -H 'Host: evil.example.com' https://<新ホスト>/login
# 転送ヘッダーの注入が効かないこと（何も出力されなければ OK）
curl -sS -H 'X-Forwarded-Prefix: /INJECTED' https://<新ホスト>/login | grep INJECTED
# セッションクッキーに Secure が付いていること（上記 3 の確認）
curl -sSI https://<新ホスト>/login | grep -i 'set-cookie'
```

⚠️ **この検証をローカル開発環境で行っても意味がありません。** `TrustHosts` は `APP_ENV=local` とテスト実行時には自動で無効化されるため（`shouldSpecifyTrustedHosts()`）、偽装 Host でも 200 が返ります。検証は本番・ステージングで行ってください。

400 になった場合は `storage/logs` に `不正なリクエストを拒否しました（Host ヘッダー等）` の warning が出ます（1 分あたり 60 件まで）。届いた `Host` の実値と拒否理由（`Untrusted Host` など）が記録されるので、切り分けに使ってください。

⚠️ ロードバランサや監視から `/up`（ヘルスチェック）を叩く場合も、`Host` が許可リストのいずれかと一致していないと 400 になります。IP 直打ちで監視している場合は、その IP / ホスト名を `TRUSTED_HOSTS` に追加してください（`.env` の変更と `docker compose ... restart laravel` で反映されます。上記 7 参照）。

### 5. ACME（Let's Encrypt）の認証方式を把握しておくこと

> **【2026-08-31 更新・Issue #90】** 以前は nginx コンテナの 443 ブロックが `location /` ひとつで全経路を `proxy_pass` していたため、`/.well-known/acme-challenge/...` が Laravel まで到達し、**HTTP-01 チャレンジが `trustHosts` の許可リストの影響を受けていました**。現在は `nginx-proxy/default.conf` の 80 / 443 の両方に ACME 専用の `location ^~ /.well-known/acme-challenge/` を置いたため、**チャレンジは Laravel に届かず `trustHosts` の影響を受けません。** 以下は認証方式ごとの挙動の整理と、設定が巻き戻ったときの切り分け材料として残しています。

laravel コンテナ内の Nginx（`laravel/docker/nginx/default.conf`）も `location ~ /\.(?!well-known).*` で `.well-known` を除外しているため、仮に前段の ACME location が無くなってもリクエスト自体は Laravel に届きます（そこで `trustHosts` に弾かれます）。

```bash
# 認証方式の確認（webroot / standalone / nginx のいずれか）
grep -n 'authenticator' /etc/letsencrypt/renewal/*.conf
```

> **📌 2026-08-31 時点の本番 EC2 の実態（Issue #90 で調査）**
>
> | 項目 | 実際の値 |
> |---|---|
> | 証明書名 | `54-168-196-65.nip.io`（`nip.io` によるワイルドカード DNS。独自ドメインは未取得） |
> | 有効期限 | 2026-11-19 |
> | `authenticator` | `standalone` |
> | `pre_hook` | `docker compose -f .../docker-compose.prod.yml -p trainingrepo-prod stop nginx` |
> | `post_hook` | 同上 `start nginx` |
> | 自動更新 | **一度も走っていない**。`/etc/crontab` に certbot の行はあるが、`cronie` が未導入で `crond` が存在しない |
>
> つまり下表の `standalone` 行が該当しますが、**pre-hook で nginx コンテナを止めてから certbot が :80 を掴む**構成になっているため、「bind できず実行できない」状態にはなっていません。代わりに **更新のたびに nginx が数十秒停止します**。
>
> **⚠️ 自動更新が動いていないため、このままでは 2026-11-19 に証明書が失効し HTTPS が全面停止します。** 「EC2 起動後の初期セットアップ手順」の 10〜12（cronie の導入・cron 設定・`--dry-run` 検証）を実施してください。

| 認証方式 | 影響 | 対応 |
|---|---|---|
| `nginx`（certbot の nginx プラグイン） | 影響なし。certbot が一時的に ACME 用の `location` を挿すため、Laravel には届きません | 不要 |
| `webroot` | **ACME location が有効なら影響なし。** 前段 Nginx の ACME location が失われている場合のみ、新ホストの証明書取得が 400 で失敗します（`APP_URL` はまだ旧ホストのため、チャレンジのリクエストが `trustHosts` で弾かれる） | `nginx-proxy/default.conf` の ACME location を確認する。無い場合は上記手順 2（`TRUSTED_HOSTS` への追加）を証明書取得より前に行う |
| `standalone`（**現行**） | **`trustHosts` の影響は受けません**（certbot が自前で :80 に HTTP サーバを立てて応答するため、リクエストは Laravel まで届きません）。nginx コンテナが :80 を掴んでいますが、pre-hook で停止させることで bind できるようにしています | `TRUSTED_HOSTS` は無関係。**更新のたびに nginx が停止する**点に注意 |

> **⚠️ `standalone` の失敗は上の 2 つと症状も対処も別物です。** 400 ではなく「ポートが使用中で bind できない」というエラーになります（pre-hook が正しく設定されていない、または nginx の停止に失敗した場合）。切り分けの際に混同しないでください。

**恒久的には、`webroot` 方式に切り替えて nginx を止めずに更新できるようにするほうが安定します。** 更新中のダウンタイムが無くなり、証明書の更新がアプリの設定状態にも依存しなくなります。

`nginx-proxy/default.conf` には ACME 用の location を 80 / 443 の両方に設定済みです（Issue #90 で追加）。

```nginx
# nginx コンテナの 80 / 443 ブロックの、location / より前に置く
location ^~ /.well-known/acme-challenge/ {
    root /var/www/certbot;
    default_type "text/plain";
}
```

`docker-compose.prod.yml` の名前付きボリューム `certbot_webroot` が nginx コンテナの `/var/www/certbot` に**読み取り専用で**マウントされています。書き込むのはホスト側の certbot で、実体は `/var/lib/docker/volumes/trainingrepo-prod_certbot_webroot/_data` です。次のコマンドで認証方式を切り替えます。

```bash
# ホスト側の certbot から webroot 方式で再取得（方式変更のみ。--force-renewal は不要）
sudo certbot certonly --webroot -w /var/lib/docker/volumes/trainingrepo-prod_certbot_webroot/_data \
  -d <ホスト名> --cert-name <ホスト名>

# 更新設定から不要になった hook を削除
sudo vi /etc/letsencrypt/renewal/<ホスト名>.conf
#   pre_hook / post_hook の2行を削除し、authenticator = webroot になっていることを確認

# 移行後は nginx を止めないので、更新時のリロードを deploy-hook で行う
sudo sed -i 's|certbot renew -q|certbot renew -q --deploy-hook "docker compose -f /home/ec2-user/TrainingRepo/docker-compose.prod.yml -p trainingrepo-prod exec -T nginx nginx -s reload"|' \
  /etc/cron.d/certbot-renew

sudo certbot renew --dry-run
```

> 切り替えは Issue #90 の対応手順書（`Issue90_作業手順.md`）の「webroot への移行（任意）」に詳細があります。**必須ではありません。** まずは自動更新の cron を入れて失効を止めることが最優先です。

> ⚠️ 認証方式にかかわらず、**「更新できる状態か」と「更新が実際に走るか」は別問題です。** 本番ではまさに後者が抜けていました（Issue #90）。次の 2 つを定期的に確認してください。
>
> ```bash
> sudo certbot certificates          # 有効期限
> sudo certbot renew --dry-run       # 更新手順が最後まで通るか
> cat /etc/cron.d/certbot-renew      # 更新を起動する仕組みが実在するか
> ```

### 6. ログインがロックされたときの解除手順を把握しておくこと

ログイン試行のレート制限は 2 段構えです（`LoginRequest::ensureIsNotRateLimited`）。

| 段 | キー | 上限 | 解除 |
|---|---|---|---|
| 第 1 段 | メールアドレス ＋ 送信元 IP | 5 回 / 1 分 | 最大 1 分で自然に解除 |
| 第 2 段 | **メールアドレスのみ** | 10 回 / 15 分 | 最大 15 分で自然に解除。即時解除は下記コマンド |

**第 2 段は送信元 IP を見ないため、外部から任意のアカウントを狙ってロックできます。** 攻撃者が送信元を分散させれば第 1 段に一度も掛からずに 10 回到達させられ、その間は**正しいパスワードを持つ本人もログインできません**（`Auth::attempt` より前で弾かれるため）。本アプリの管理操作はすべてログインの先にあるので、全管理者のアドレスを同時に狙われると復旧の入口自体が消えます。

```bash
# 特定アカウントのロックだけを即時解除する
docker compose -f docker-compose.prod.yml -p trainingrepo-prod exec laravel \
  php artisan auth:unlock admin@example.co.jp
```

> **⚠️ `php artisan cache:clear` で代用しないこと。** 全レート制限が一斉に消えるため、**進行中のブルートフォースに対する防御ごと消えます**（`CACHE_STORE=database` のためセッションは巻き込まれませんが、レート制限は全件消えます）。`auth:unlock` は指定した 1 アカウントのカウンタだけをリセットします。
>
> 第 1 段（送信元 IP 単位）は攻撃元 IP に紐づくため、このコマンドでは解除しません。本人の環境からは最大 1 分で自然に解けます。

継続的にロックされる場合は、`storage/logs` のログイン失敗と、前段 Nginx のアクセスログで送信元を確認してください。窓が 15 分なので、攻撃者は**ロックを維持するだけで 10 リクエスト / 15 分を送り続ける**必要があります。

### 7. 証明書の自動更新が「実在する」ことを確認すること

**設定ファイルが存在することと、それが実行されることは別です。** 2026-08-31 の調査では、`/etc/crontab` に certbot の行が書かれていたにもかかわらず、**`cronie` が未導入で `crond` が存在せず、更新が一度も走っていませんでした**（Issue #90）。Let's Encrypt の証明書は 90 日で失効し、失効すればブラウザが接続を拒否するため **HTTPS が全面停止**します。

**確認は「設定の有無」ではなく「実行される状態か」で行ってください。** 順に3つです。

```bash
# ① cron デーモンが動いているか ← ここが今回の落とし穴
systemctl is-active crond

# ② 更新を起動する設定が実在するか
cat /etc/cron.d/certbot-renew || sudo crontab -l | grep certbot || tail -1 /etc/crontab

# ③ 更新手順が最後まで通るか（実際には更新しない）
sudo certbot renew --dry-run

# ④ 現在の有効期限
sudo certbot certificates
```

| 症状 | 原因 | 対処 |
|---|---|---|
| ① が `inactive` / `unknown` | **cronie が未導入**（AL2023 の最小構成には入っていません） | `sudo dnf install -y cronie && sudo systemctl enable --now crond` |
| ② が何も返さない | 更新設定そのものが無い | 初期セットアップ手順 11 を実行する |
| ③ が失敗する | 認証方式と実構成のずれ（ポート競合・ACME location 欠落など） | 上記 5 の表で認証方式を確認する |
| ③ は通るが期限が縮まらない | cron は動いているが期限 30 日前に達していないだけ | 正常。①〜③が通っていれば問題ない |

> **⚠️ `/etc/cron.daily` や `/etc/crontab` が存在することは、cron が動いている証拠になりません。** これらは cronie 抜きでも存在します。必ず ① を見てください。

> **`--dry-run` は `standalone` 運用では pre/post hook を実行するため nginx が短時間停止します。** アクセスの少ない時間帯に実施してください。`webroot` へ移行済みなら停止しません。

### 8. 秘匿値を compose ファイルに直書きしないこと

`docker-compose.prod.yml` はリポジトリ管理下（Issue #90）です。パスワードを直書きするとリポジトリに認証情報が残り、履歴からも消せません。

| 値 | 置き場所 |
|---|---|
| `MYSQL_ROOT_PASSWORD` | リポジトリ直下の `.env`（`.gitignore` 済み）。compose 側は `${MYSQL_ROOT_PASSWORD:?...}` で参照 |
| `DB_PASSWORD` / `APP_KEY` / AWS キー | `laravel/.env`・`python/.env`（ともに `.gitignore` 済み。`.dockerignore` でイメージにも入りません） |

```bash
# compose ファイルに秘匿値が残っていないか（何も出なければ OK）
grep -nE '^\s+[A-Z_]*(PASSWORD|SECRET|KEY)[A-Z_]*\s*[:=]\s*[^$[:space:]]' docker-compose.prod.yml
```

雛形は `.env.prod.example` にあります。**値は入れずにキー名だけ**を管理してください。

- **ドメイン必須**：Let's Encrypt はIPアドレスへの証明書発行に対応していません。ドメイン取得、または `nip.io` のようなワイルドカード DNS サービスの利用が前提となります（現行本番は `nip.io` を使用）
- **単一障害点**：EC2が1台のため、インスタンス停止でサービス全体が停止します。研修用途では許容範囲です
- **データ永続化**：MySQLデータの保持には docker-compose.yml の volumes 定義が必須です（セットアップ手順 §4 参照）。加えてEBSスナップショットの定期取得を推奨します
- **Elastic IP の課金**：EC2を長時間停止する場合、関連付け中のElastic IPに課金が発生します。研修終了時はElastic IPの解放も忘れずに行ってください
- **Bedrockリージョン**：使用するClaudeモデルが利用可能なリージョンを確認してください（東京リージョン: ap-northeast-1）
