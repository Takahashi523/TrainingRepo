## 1. はじめに

### 1.1 本書の位置付け

「国内SES向け 人材・案件マッチングシステム Nexus」のインフラ基盤であるAWSの設計を記載したドキュメントである。 本構成では、構築・運用の簡素化および研修費用の圧縮を目的に、**EC2 1台＋Docker Compose**によるシンプル構成を採用する。

---

### 1.2 コスト最適化に伴う制約とリスク
本構成は「最小インフラ投資でのHTTPS環境構築」を最優先しているため、以下の制約がある。

- **単一障害点 (SPOF):** EC2が1台のため、インスタンスの停止やホスト障害発生時にサービス全体が完全に停止する。研修用途としては許容範囲とする。
- **データロストリスク:** DBはEC2内のDockerボリューム（EBSローカル）に保存される。`docker compose down` 時などのデータ消失を防ぐためボリューム定義を必須とし、あわせてEBSスナップショットの定期取得を推奨する。
- **リソース競合:** Web、AIエンジン、DB、Nginxがすべて同一ホストのメモリ・CPUを分け合うため、同時アクセス増大時にパフォーマンスが劣化する可能性がある。

## 3. ネットワーク (VPC・セキュリティグループ)

### 3.1 VPC・サブネット
EC2内にすべてのコンテナを内包するため、パブリックサブネット1つのシンプルな構成とする。

| リソース名 | 種別 | CIDRブロック | 配置コンポーネント / 備考 |
| :--- | :--- | :--- | :--- |
| **Nexus-vpc** | VPC | `10.0.0.0/16` | 研修環境全体の親ネットワーク。 |
| **Nexus-pub-sub** | サブネット | `10.0.1.0/24` | **EC2インスタンス (Elastic IP付与)** を配置。|

### 3.2 セキュリティグループ設計 (`Nexus-ec2-sg`)
外部からのアクセスはWeb通信（HTTP/HTTPS）のみに制限し、管理用のポートは一切開放しない。

#### インバウンドルール
| 優先度 | タイプ | プロトコル | ポート範囲 | ソース | 備考 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | HTTPS | TCP | `443` | `0.0.0.0/0` | インターネット全体からのWebアクセスを許可。|
| 2 | HTTP | TCP | `80` | `0.0.0.0/0` | Let's Encryptの認証、およびHTTPSへのリダイレクト用。|
| ※ | SSH | TCP | `22` | - | **【全面禁止】** 開放せず、Session Managerを使用。|

#### アウトバウンドルール
| 優先度 | タイプ | プロトコル | ポート範囲 | 送信先 | 備考 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | すべてのトラフィック | すべて | すべて | `0.0.0.0/0` | デフォルト設定（外部APIやBedrockなどへの通信用）。 |

## 4. 計算基盤・データ層 (EC2ホスト仕様)

コンテナを4つ同時に稼働させるため、メモリ不足によるタスクキルを防止可能なスペックを定義する。

| 設定項目 | 推奨設定値 | 備考 / 設定のポイント |
| :--- | :--- | :--- |
| **インスタンスタイプ** | `t3.small` (最低) / `t3.medium` (推奨) | 4コンテナ同時起動のため1GBのt2.microは不可。|
| **OS** | `Amazon Linux 2023` | 最新の標準Linux環境。|
| **ストレージ** | `20 GiB` (`gp3`) | OS、Dockerイメージ、MySQLの永続データをすべて格納。|
| **IPアドレス** | `Elastic IP (EIP)` | 必須。インスタンス再起動時のIP変動を防ぎドメインと固定で紐付ける。|

## 5. コンテナオーケストレーション (Docker Compose)

EC2ホスト上で `docker compose up -d` により一元管理されるコンテナ群の定義。ホスト外部にポートを露出させるのは `nginx` のみとし、他のコンテナはすべて外部非公開（内部通信のみ）とする。

### 5.1 コンテナ構成一覧
| コンテナ名 | ベースイメージ | 内部ポート | 外部公開 | 用途・備考 |
| :--- | :--- | :--- | :--- | :--- |
| **nginx** | Nginx | `443` / `80` | **✅ 公開** | SSL終端、HTTPSリダイレクト、リバースプロキシ。|
| **laravel** | PHP 8.3 + Node.js 22 | `8000` | ❌ 内部のみ | Laravel + React (Inertia.js) アプリ本体。|
| **python** | Python 3.12 + FastAPI | `8001` | ❌ 内部のみ | FastAPIによるマッチング・AI処理エンジン。|
| **mysql** | MySQL 8.4 | `3306` | ❌ 内部のみ | ユーザー・案件データ管理用データベース。|

### 5.2 データ永続化・自動起動設計
- **データ永続化:** `mysql` サービスに対し、必ず名前付きボリューム（`mysql-data:/var/lib/mysql`）をマッピングし、コンテナ破棄時にデータが全消失するのを防ぐ。
- **自動起動:** 各サービスに `restart: always` を定義し、EC2インスタンス自体の再起動時にもシステムが自動復旧するように制御する。

## 6. SSL・ドメイン・外部サービス連携

### 6.1 ドメインと名前解決 (Amazon Route 53)
Let's EncryptはIPアドレス直打ちでの証明書発行に対応していないため、独自ドメインの取得を必須とする。
- Route 53等でドメインを取得し、ホストゾーンのAレコードをEC2に付与した **Elastic IP** へ向ける。

### 6.2 SSL証明書 (Certbot / Let's Encrypt)
- **取得・配置:** EC2ホスト側にCertbot環境（Python venvベース）を構築し、Nginx経由で90日制限の無料SSL証明書を取得する。
- **自動更新:** `cron` にて1日2回 `certbot renew` をチェックするタスクを設定し、有効期限残り30日未満で自動更新を実行する。

### 6.3 AIエンジン (Amazon Bedrock)
- **認証方式:** `python` コンテナからのBedrock API（boto3）呼び出しは、EC2にアタッチされたIAMロールを利用するため、`.env` への認証キー埋め込みは不要。
- **モデル利用:** `ap-northeast-1`（東京リージョン）で有効化した Claude モデルをオンデマンドで呼び出す。
- **仕様補足:** マッチングスコアはルールベースではなくAI総合判定とし、結果はDB保存せずオンデマンド計算とする。

## 7. データフロー・通信経路一覧

| 送信元 | 送信先 | プロトコル/ポート | 内容・通信の性質 |
| :--- | :--- | :--- | :--- |
| ユーザー（PCブラウザ） | nginxコンテナ | HTTPS (443) | システムへの外部アクセス（暗号化）|
| ユーザー（PCブラウザ） | nginxコンテナ | HTTP (80) | アクセス時にHTTPS（443）へ自動リダイレクト|
| nginxコンテナ | laravelコンテナ | HTTP (8000) | SSL終端後のリクエスト転送（Docker内部通信）|
| laravelコンテナ | pythonコンテナ | HTTP (8001) | マッチング・AI処理のリクエスト（Docker内部通信）|
| laravelコンテナ | mysqlコンテナ | TCP (3306) | データベースへのクエリ発行（Docker内部通信）|
| pythonコンテナ | Amazon Bedrock | HTTPS (443) | AWS SDK (boto3) を経由したLLM API呼び出し|
| pythonコンテナ | Google Maps API | HTTPS (443) | Distance Matrix APIを利用した距離情報の取得|
