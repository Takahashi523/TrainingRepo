### 3.1 除外条件（ハードフィルタ：スコア計算前に適用）
※ステータスによる絞り込み（案件＝募集中 / 人材＝提案可 等）は API 呼び出し側で実施済みであることを前提とする。

### 注記

### 3.2 配点表（100点満点）

| # | 評価項目 | 配点 | 判定ロジック（暫定） | 満点の条件 | 部分点の扱い | ステータス | 入力要素# |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| S1 | **必須スキル経験年数充足度** | 30 | F1通過者を対象に、案件の必須スキル各々について「人材の経験年数 / 必要年数」の充足率を算出（上限1.0） | 全必須スキルで経験年数が必要年数以上（充足率が全て1.0） | 比例和方式（充足率の平均 × 30点）。各スキルの充足率は1.0で頭打ち（経験超過を加算しない）。1スキル極端不足の影響を他でカバー可能な連続スコアになる。 | 🟡 **【暫定】** | #1, #2 |
| S2 | **工程経験一致** | 20 | 案件の対象工程と人材の経験工程の重なりで判定。計算式：S2 = \|案件対象工程 ∩ 人材経験工程\| ÷ \|案件対象工程\| × 20 | 案件対象工程をすべて経験あり（充足率 = 1.0） | 比例和。例：案件対象=4工程、人材経験で3つ重複 → (3/4) × 20 = 15点。案件側で対象工程が複数指定されたケースを想定。 | 🟡 **【暫定】** | #3 + 案件側 projects.required_processes |
| S3 | **尚可スキル一致** | 10 | 案件の尚可（あれば嬉しい）スキルと人材の経験スキルの重なりで判定。計算式：S3 = \|案件尚可スキル ∩ 人材経験スキル\| ÷ \|案件尚可スキル\| × 10 | 案件尚可スキルをすべて経験あり（充足率 = 1.0） | 比例和。例：案件尚可=3スキル、人材保有で2つ重複 → (2/3) × 10 = 6.7点。尚可スキルは『必要年数』判定なし（保有有無のみで判定、経験年数は問わない）。 | 🟡 **【暫定】** | #1 + 案件側 projects.preferred_skills |
| S4 | **勤務形態一致** | 10 | 案件の稼働形態と人材の勤務形態タグの適合度で判定 | 人材タグに案件の稼働形態が含まれる | 人材＝『フルリモート希望』× 案件＝『常駐』は0点等、マトリクスを 3.3節 で定義予定。 | 🟡 **【暫定】** | #9 |
| S5 | **勤務地/通勤条件一致** | 10 | 実通勤時間（estimate_commute_time(#5 最寄駅, #6 勤務地駅)）で段階判定。両者フルリモート時は満点扱い。 | 実通勤時間 ≤ 30分、または両者フルリモート一致 | 実 ≤ 30分 → 10点 / ≤ 60分 → 7点 / ≤ 90分 → 4点 / それ以上 → 0点。 | 🟡 **【暫定】** | #5, #6 |
| S6 | **単価一致** | 10 | 人材の希望単価が案件の単価レンジ内に収まるか | case_rate_min ≤ desired_rate ≤ case_rate_max | レンジ内 = 10 / 上限超過幅5万以内 = 5 / 希望単価NULL = 加点対象で10点扱い / QA#14 でスキル見合いは満点扱い。 | 🟡 **【暫定】** | #10, #11 |
| S7 | **稼働開始時期一致** | 5 | 人材の稼働可能時期 ≤ 案件の参画開始時期 + 猶予期間 | 人材稼働可能日 ≤ 案件開始日 | 差分30日以内 = 5 / 60日以内 = 3 / それ以上 = 0（暫定）。 | 🟡 **【暫定】** | #7, #8 |
| S8 | **顧客折衝/人物要件一致** | 5 | 案件が『顧客折衝要』の場合、人材の『顧客折衝経験=有』で満点。案件『不問』は満点扱い。 | 案件要求=要 and 人材=有 | 要求=『要』で人材=『無』の場合は0点。 | 🟡 **【暫定】** | #4 |
| | **合計** | **100** | | | | | |

### 3.3 勤務形態マトリクス（S4の判定表）【暫定】

人材側の希望（タグ）と案件側の稼働形態の組み合わせに基づき、10点満点で配点する。

| :--- | :---: | :---: | :---: |

| **一部リモート可のみ** | 7 | 10 | 3 |
| **フルリモート希望** | 0 | 5 | 10 |

### 5.5 LLMプロバイダ選定根拠（Bedrock採用理由）
本設計書は AWS Bedrock / Claude 3.5 Sonnet を前提とする。OpenAI API 等の外部LLMではなく Bedrock を採用する根拠を以下に整理する。

| 観点 | Bedrock Claude 3.5 Sonnet （採用） | OpenAI API （比較） | 決め手 / 関連QA |
| :--- | :--- | :--- | :--- |
| **データガバナンス** | VPCエンドポイント経由でAWS網内完結。個人情報が外部ネットに出ない。顧客データのモデル学習非利用がデフォルト契約。 | 外部egressが発生（米国リージョン経由など）。DPIA／契約上のオプトアウト対応が別途必要。 | QA#25 個人情報保護 |
| **インフラ統一** | ECS/RDS/S3と同一AWS。IAMロールで認証完結、APIキー発行・ローテ不要。 | OpenAI APIキーの発行・Secrets Manager格納・定期ローテが必要。AWS外契約で別請求。 | 運用負荷・漏洩リスク |
| **プロバイダ依存回避** | 同一SDK(boto3 bedrock-runtime)で Claude/Llama/Titan/Mistral等を切替可能。差替はmodel_id変更のみ。 | OpenAI SDK／エンドポイントに固定。乗換時はクライアント層ごと再実装。 | QA#29 プロバイダ依存回避要望 |
| **日本語・構造化出力** | Claude 3.5 Sonnet は日本語推論・JSON構造化出力に強い。推薦理由／経歴要約用途に好適。 | GPT-4o 系も同等水準。性能差は決定打にならず。 | 性能要因は中立 |
| **監査ログ** | CloudTrailで InvokeModel・トークン数・呼出元IAMまで自動記録。 | アプリ側で別途ログ設計が必要（リクエスト／レスポンスをDBに保存等）。 | QA#25 操作ログ保存 |
| **コスト** | AWS請求一本化。NAT GW経由のegressコスト発生せず。Sonnetトークン単価も競争力あり。 | 別契約・別予算承認フロー。NAT GW egress 転送量課金が乗る。 | 運用予算 |
| **待機時間（QA#30）** | Sonnetストリーミング対応で 5-10 秒同期要件を安定して満たす。 | GPT-4o 系も満たせる。差別化要因にはならず。 | QA#30 許容待機時間 |
| 結論 | QA#25（個人情報）・QA#29（プロバイダ依存回避）・運用統一性の3点から Bedrock 優位。OpenAI を選ぶ合理性は、既存のOpenAIプロンプト資産／Function calling依存コードが社内に大量にある場合に限られる。本プロジェクトでは該当しないため Bedrock を正式採用提案する（PM上申待ち）。 |
