## 3. マッチング判定プロンプト

### 3.1 概要

Bedrock Claude 3.5 Sonnet に対し、人材プロフィールと案件要件を読み込ませ、**0〜100点の総合適合度スコア**と **判定理由・推薦コメント・不足条件** を JSON 構造化出力させる。配点感覚は**旧設計（マッチングエンジン設計書 v0.3 までの S1〜S8 ルールベース配点）から転用**し、ガイドラインとして User プロンプトに埋め込む（ハードフィルタ・床ルールは設けず、AI の総合判定に委ねる）。

| 項目 | 仕様 |
| :--- | :--- |
| モデル | anthropic.claude-3-5-sonnet-20240620-v1:0 |
| パラメータ | max_tokens=800 / temperature=0.3 / top_p=0.9 |
| 出力形式 | JSON 構造化出力 |
| 1回呼出で生成する項目数 | 5項目（match_score / match_rank / ai_score_reason / ai_comment / ai_missing）|

> **1回呼出 5項目生成の理由**：5項目は同じ判断の異なる側面であり、別呼出にすると整合性が崩れる（例：match_score=80 なのに ai_score_reason に「経験不足」と書かれる）。同一推論内で生成することで整合性・コスト・速度を担保する。

---

### 3.2 System プロンプト

```
あなたはSES営業を補助するアシスタントです。
以下の人材情報と案件情報を読み、人材が案件にどの程度適合するかを総合判定し、
必ず指定の JSON 形式で出力してください。

判定の原則：
- 提示データの範囲で回答してください。記載のない事項について推測や断定はしないでください。
- ソフトスキル（マネジメント経験・上流工程経験・議事録作成経験等）はアピールポイントおよび人材スキルの自由記述から判断してください。
- 単価・稼働時期・勤務形態・勤務地などの定量条件は厳密に判定してください。
- 説明・推薦コメントは事実ベースで簡潔に書いてください。
- 後述の【判定観点と配点目安】に従って各観点ごとに点数を算出し、合計して総合スコアを決定してください。
- match_score は各観点の点数の合計値と必ず一致させること。AI独自の総合判断による値ではなく、上記の足し算結果をそのまま出力すること。
```

### 3.3 User プロンプト テンプレート

```
以下の人材と案件のマッチングを総合判定してください。

【人材プロフィール】
- アピールポイント: {H1}
- 顧客折衝経験: {H2 → "有" or "無"}
- 稼働可能時期: {H3}
- 希望単価: {H4} 万円/月(NULL の場合は "希望なし")
- 最寄駅: {H5}
- 経験工程: {H6〜H11 のうち値=1 のラベルをカンマ区切り}
- 勤務形態希望: {H12〜H14 のうち値=1 のラベルをカンマ区切り}
- 保有スキル:
{H15(engineer_skills) を以下の形式で全件列挙}
  - {label}: {detail}
  - {label}: {detail}
  ...

【案件情報】
- 業務内容詳細: {P1}
- 顧客折衝経験要否: {P2 → "要" or "不問"}
- 参画開始時期: {P3}
- 単価レンジ: {P4}〜{P5} 万円/月(備考: {P6})
- 稼働形態: {P7 → "常駐" or "一部リモート可" or "フルリモート"}
- 勤務地: {P8}
- 対象工程: {P9〜P14 のうち値=1 のラベルをカンマ区切り}
- 必須スキル:
{P15(project_skills where skill_type='required') を以下の形式で全件列挙}
  - {label}: {detail}
- 尚可スキル:
{P16(project_skills where skill_type='preferred') を以下の形式で全件列挙}
  - {label}: {detail}

【判定観点と配点目安】
合計100点満点で総合判定してください。各観点の配点と判定基準を以下に示します。

■ 必須スキル充足度(最大30点)
- 案件の必須スキル(P15)を人材(H15)がどの程度満たしているかを判定
- project_skills.detail から「必要年数」を読み取り、engineer_skills.detail から「経験年数」を読み取って充足率を算出
- 充足率の比例和方式: (各スキルの充足率の平均) × 30
- 各スキルの充足率は1.0(必要年数以上)で頭打ち、経験超過は加点しない
- 必須スキルを1つも保有していない場合: 0点
- **かつ、上記計算で算出した総合スコアから30点を減点する**（必須スキル全不足の人材は構造的にDランクに落とすため）

■ 工程経験適合度(最大20点)
- 案件の対象工程(P9〜P14のうち値=1)と人材の経験工程(H6〜H11のうち値=1)の重なりで判定
- 計算式: |案件対象工程 ∩ 人材経験工程| ÷ |案件対象工程| × 20
- 例: 案件対象=4工程・人材経験で3つ重複 → (3/4) × 20 = 15点

■ 尚可スキル適合度(最大10点)
- 案件の尚可スキル(P16)を人材(H15)がどの程度満たしているかを判定
- 経験年数判定なし、保有有無のみで充足率を算出
- 計算式: |案件尚可スキル ∩ 人材保有スキル| ÷ |案件尚可スキル| × 10
- 案件に尚可スキルが無い場合は満点扱い(10点)

■ 勤務形態適合度(最大10点) ※マトリクス判定
人材タグ(H12〜H14のうち値=1) ／ 案件稼働形態(P7):
- 常駐可のみ × 常駐         : 10
- 常駐可のみ × 一部リモート可  : 10
- 常駐可のみ × フルリモート    :  0
- 一部リモート可のみ × 常駐    :  7
- 一部リモート可のみ × 一部    : 10
- 一部リモート可のみ × フル    :  3
- フルリモート希望のみ × 常駐  :  0
- フルリモート希望のみ × 一部  :  5
- フルリモート希望のみ × フル  : 10
- 常駐可+一部リモート可 × フル :  3
- 全タグ保有 × 任意           : 10

■ 勤務地/通勤適合度(最大10点)
- あらかじめ外部API（Google Maps Distance Matrix API）で算出された通勤時間（分単位）を {commute_time_minutes} として入力で渡すため、その値に基づいて配点する
- 実通勤時間 ≤ 30分 → 10点
- ≤ 60分 → 7点
- ≤ 90分 → 4点
- それ以上 → 0点
- 両者フルリモート時(人材H14=1かつ案件P7='remote') → 10点扱い（通勤時間は判定対象外）
- 通勤時間がNULL（外部API算出失敗）の場合は0点扱いとし、その旨を ai_score_reason に明記

■ 単価適合度(最大10点)
- 人材希望単価(H4)が案件単価レンジ(P4〜P5)内に収まるか
- レンジ内: 10点
- 上限超過幅5万円以内: 5点
- 希望単価NULL("希望なし"): 加点対象で10点扱い
- 単価備考(P6)に「スキル見合い」等あり、かつ rate_min/max がNULL: 満点扱い(10点)
- レンジを大きく外れる場合: 0点

■ 稼働開始時期適合度(最大5点)
- 人材稼働可能時期(H3) ≤ 案件参画開始時期(P3): 5点
- 案件開始から30日以内に稼働可能: 3点
- 60日以内: 1点
- それ以上遅い: 0点

■ 顧客折衝/人物要件適合度(最大5点)
- 案件P2='要' × 人材H2=1(有): 5点
- 案件P2='不問': 満点扱い(5点)
- 案件P2='要' × 人材H2=0(無): 0点
- 加えて、案件P1業務内容詳細にマネジメント経験・上流工程経験等のソフトスキル要件が含まれる場合、人材H1アピールポイント/H15スキル詳細から該当記述を探索して反映

合計 = 必須スキル + 工程経験 + 尚可スキル + 勤務形態 + 勤務地 + 単価 + 稼働開始時期 + 顧客折衝/人物要件
(理論上の最大値 = 100点)
※ 必須スキル該当0の場合は、上記合計からさらに-30点ペナルティを適用
ai_score_reason には、各観点での点数の根拠を簡潔に記述してください

【スコア閾値(match_rank 判定)】
A: 80〜100点(即提案レベル)
B: 65〜79点(検討可能)
C: 50〜64点(条件交渉次第)
D: 0〜49点(見送り推奨)

【重要・厳守事項】
match_score は上記「合計 = 必須スキル + 工程経験 + ... + 顧客折衝/人物要件」の計算結果と完全に一致させること。
独自の総合判断で値を変えてはならない。

【スコアのクランプ処理】
合計値が0未満（マイナス）になる場合は、必ず 0 として出力すること。
match_score は必ず 0〜100 の整数で出力すること。

【出力フォーマット(厳守・他の文章は一切出力しないこと)】
{
  "match_score": <0〜100 の整数。0未満になる場合は0として出力>,
  "match_rank": "<A | B | C | D>",
  "ai_score_reason": "<スコアの根拠説明。200字以上300字以下で記述。適合点と不足点を両方触れる>",
  "ai_comment": "<推薦理由。150字以上250字以下で記述。営業担当が顧客に伝えられる文面>",
  "ai_missing": "<満たしていない要件の説明。50字以上150字以下で記述。すべて満たしている場合は『特になし』>"
}
```

> **NULL 値の扱い**：希望単価が NULL の場合は「希望なし」、その他項目が NULL の場合は「未入力」と埋め込む。

> **0/1 値の変換**：has_negotiation_exp / proc_* / work_style_* などの TINYINT(1) は「有/無」「あり/なし」等のラベルに変換してから埋め込む。

### 3.6 エラー処理

| エラー種別 | 処理 |
| :--- | :--- |
| JSON パース失敗 | 1回リトライ（形式特化の専用プロンプトで再呼出） |
| リトライ後も失敗 | 該当案件はマッチング結果から除外（他案件は処理継続） |
| Bedrock タイムアウト | 指数バックオフでリトライ（初回1秒、最大3回） |
| Bedrock スロットリング | 指数バックオフでリトライ |
| Bedrock 認証エラー / 不正リクエスト | 即時エラー応答（HTTP 500） |

---

### 3.6.1 JSONパース失敗時のリトライ専用プロンプト

通常プロンプトでJSONパースが失敗した場合、同一プロンプトで再呼出しても同じエラーが再発する可能性が高い。リトライ時は以下の形式特化プロンプトを使用する。

【リトライ用 System プロンプト】
```
あなたはSES営業を補助するアシスタントです。
前回出力はJSON形式違反でした。指定のJSONスキーマに従い、JSONオブジェクトのみを出力してください。
説明文・前置き・コードフェンスは一切含めないでください。
```

【リトライ用 User プロンプト】
通常プロンプトと同一の入力を渡すが、末尾に以下を追加：
```
※ 前回出力は JSON 形式違反でした。{match_score, match_rank, ai_score_reason, ai_comment, ai_missing} の5キーを持つ純粋なJSONオブジェクトのみを出力してください。
```

## 4. 人材プロフィール要約プロンプト

### 4.1 概要

`engineers.appeal_note` を入力として、人材の強み・特徴を要約したテキストを生成し、`engineers.ai_summary` に保存する。マッチング画面ではなく人材詳細画面（WF_05）で表示される。

| 項目 | 仕様 |
| :--- | :--- |
| モデル | anthropic.claude-3-5-sonnet-20240620-v1:0 |
| パラメータ | max_tokens=600 / temperature=0.3 / top_p=0.9 |
| 出力形式 | プレーンテキスト |

---

### 4.2 System プロンプト

```
あなたはSES営業を補助するアシスタントです。
人材のアピールポイントを読み、強み・特徴を簡潔に要約してください。
事実に基づき、提示データの範囲で回答してください。
推測や断定は避け、書かれていない情報は要約に含めないでください。
```

---

### 4.3 User プロンプト テンプレート

```
以下のアピールポイントから、人材の強み・特徴を 300〜400字程度で要約してください。
箇条書きではなく、自然な日本語の文章で記述してください。

【アピールポイント】
{appeal_note}
```

---

### 4.4 出力フォーマット

* プレーンテキスト、300〜400字
* 改行可（段落区切りとして使用可）
* マークダウン記法（**太字** や - 箇条書き等）は使用しない

### 4.5 想定トークン数

| 区分 | 概算 |
| :--- | :--- |
| 入力（appeal_note + プロンプト指示）| 約 1,500 トークン |
| 出力（要約テキスト）| 約 400 トークン |
| 合計 | 約 1,900 トークン |

---

### 4.6 エラー処理

| エラー種別 | 処理 |
| :--- | :--- |
| 空出力 | `ai_summary` は NULL のまま、`ai_summary_generated_at` も更新しない |
| Bedrock タイムアウト | 指数バックオフでリトライ（初回1秒、最大3回）|
| リトライ後も失敗 | HTTP 504 エラー応答。Laravel 側で「AI 要約生成に失敗しました」をWF_05 に表示 |

## 5. 共通方針

### 5.1 スコア閾値（マッチング判定）

| ランク | スコア帯 |
| :---: | :--- |
| A | 80〜100 |
| B | 65〜79 |
| C | 50〜64 |
| D | 0〜49 |

→ User プロンプト内に明記し、AI に match_rank 判定の基準を理解させる。
→ match_rank の閾値判定はアプリ層でも検算する（AI が誤った match_rank を返した場合の保険）。

---

### 5.2 ハルシネーション対策

| 観点 | 対策 |
| :--- | :--- |
| プロンプト指示 | 「提示データの範囲で回答」「推測・断定を避ける」を System プロンプトに明記 |
| temperature 設定 | 0.3 に設定（決定論性を高める）|
| 画面側表示 | 出力に「※AI生成」注記を表示（WF_05・WF_09）|
| 評価データセット | §6 の評価フレームで偽陽性（虚偽の高評価）を検出 |

---

### 5.3 PII マスキング

| 観点 | 方針 |
| :--- | :--- |
| 直接識別子 | 氏名（engineers.name）・氏名カナ（name_kana）・生年月日（birth_date）は AI に渡さない（プロンプトテンプレートに含めない）|
| 自由記述内の個人情報 | appeal_note 等にメールアドレス・電話番号等が含まれる場合の対応は未定（T-PROMPT-04 参照）|
| 監査ログ | CloudWatch Logs には PII 除去後のリクエストのみ記録 |

---

### 5.4 リトライ・タイムアウト

| 項目 | 設定値 |
| :--- | :--- |
| リトライ方式 | 指数バックオフ |
| 初回待機時間 | 1秒 |
| 最大リトライ回数 | 3回 |
| Bedrock 1リクエストあたりタイムアウト | 30秒 |
| Bedrock 全体のクライアントタイムアウト | 60秒 |

---

### 5.5 JSON パースエラー処理（マッチング判定のみ）

```
[Pythonでの処理フロー]
1. Bedrock から応答取得
2. 応答テキストの JSON パース試行
3. 成功 → 5項目の型・範囲チェック
   - match_score が 0〜100 の整数か
   - match_rank が "A"/"B"/"C"/"D" のいずれかか
   - その他のキーが存在するか
4. パース失敗 or 型不正 → 1回リトライ（§3.6.1 の専用プロンプトを使用）
5. 再度失敗 → 該当案件をマッチング結果から除外、エラーログ出力
```

---

### 5.6 トークン超過対策【暫定】

入力トークンが Bedrock の上限を超える可能性がある場合の対処：

| 案 | 内容 | 採用判断 |
| :--- | :--- | :--- |
| 案A | アピールポイント・業務内容詳細の先頭 N 文字に切り詰め | 採用候補 |
| 案B | 重要セクション抽出（事前に要約器を通す）| コスト2倍化のため非推奨 |
| 案C | チャンク分割して複数回呼出 + 結果統合 | 整合性確保が難しいため非推奨 |

→ 実機計測（典型的なアピールポイント・業務内容詳細のトークン数）の後に確定（T-PROMPT-03）。

## 6. テスト・評価方針

### 6.1 評価データセット

| 項目 | 方針 |
| :--- | :--- |
| サンプル収集 | 顧客同意の上で、過去の人材×案件の組合せと「マッチした/しなかった」の結果をサンプル化 |
| データ匿名化 | 氏名・会社名等の固有名詞を仮名に置換 |
| 件数目安 | 初期版で 30〜50 件、運用開始後に拡充 |
| 期待値 | 各サンプルに「期待スコア帯」（A/B/C/D）を人手でラベル付け |

---

### 6.2 スナップショットテスト

| 観点 | 方針 |
| :--- | :--- |
| 目的 | プロンプト変更による出力ブレを検出 |
| 方式 | 評価データセットの各サンプルに対してマッチング判定を実行し、出力 JSON を保存。プロンプト変更時に新しい出力と比較 |
| 比較項目 | match_score のずれ（±5点許容）、match_rank の一致、ai_score_reason / ai_comment / ai_missing の意味的類似度（cos類似度等）|
| 失敗時 | CI でアラート、リリースをブロック |

> temperature=0.3 でも出力は完全に決定的ではないため、複数回試行の平均で判定する。

---

### 6.3 精度モニタリング

| 観点 | 方針 |
| :--- | :--- |
| 営業担当フィードバック | マッチング結果のうち「採用しなかった」案件にフィードバック理由を入力できる UI を将来検討（v1.0 リリース後）|
| スコアと成約率の相関 | パイプライン上のステータス遷移（成約 / 不成立）と AI スコアの相関を月次分析 |
| トークン使用量 | CloudWatch メトリクスで日次集計 |
| エラー率 | JSON パース失敗率・タイムアウト率を CloudWatch メトリクスで監視 |
