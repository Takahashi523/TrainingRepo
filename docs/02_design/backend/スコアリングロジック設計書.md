#### 2.4.1 項目数（15 / 16）と ペア数（9）の関係

> **疑問への先回り回答**：「人材15項目・案件16項目あるのに、なぜペアが9つに減るのか？」

ペアは **1対1の単純対応ではなく「AI に判定させる観点」の単位**で集約しているため、項目数とペア数は一致しない。集約は以下の3パターンに分類される。

##### パターンA：1:1 単純対応（ペア 3 / 4 / 5 / 6）

人材側の1カラム ↔ 案件側の1カラム。例：H3 稼働可能時期 ↔ P3 参画開始時期。

##### パターンB：複数カラムを1概念に集約（ペア 7 / 8 / 9）

| ペア | 人材側 | 案件側 | 集約理由 |
| :---: | :--- | :--- | :--- |
| 7 | 勤務形態希望（H12+H13+H14 の3カラム）| 稼働形態（P7 の1 ENUM）| 「勤務形態」という1つの判定観点 |
| 8 | 希望単価（H4 の1カラム）| 単価下限+上限+備考（P4+P5+P6 の3カラム）| 「単価」という1つの判定観点 |
| 9 | 工程経験 6種（H6〜H11）| 対象工程 6種（P9〜P14）| 「経験工程」という1つの判定観点 |

##### パターンC：人材側1カラムが複数ペアにまたがる（ペア 1 / 2）

H15 人材スキルは、案件側で「必須」「尚可」の2区分に分けて評価されるため、**同じ H15 が2ペアで再利用**される。

```
        ┌─→ P15 必須スキル(ペア1)
   H15 ─┤
        └─→ P16 尚可スキル(ペア2)
```

##### 集計（ユニーク項目数で検算）

| ペア | 使う人材項目数 | 使う案件項目数 |
| :---: | :---: | :---: |
| 1 | 1 (H15) | 1 (P15) |
| 2 | 1 (H15 再利用) | 1 (P16) |
| 3 | 1 (H2) | 1 (P2) |
| 4 | 1 (H1) | 1 (P1) |
| 5 | 1 (H5) | 1 (P8) |
| 6 | 1 (H3) | 1 (P3) |
| 7 | 3 (H12〜H14) | 1 (P7) |
| 8 | 1 (H4) | 3 (P4〜P6) |
| 9 | 6 (H6〜H11) | 6 (P9〜P14) |
| **ユニーク総数** | **15** ✓ | **16** ✓ |

> **設計意図**：AI のプロンプトには 31項目（15+16）を全て渡すが、**AI に判定させる視点としては 9つの観点で適合度を評価してほしい**、という二段構えの構造になっている。AI スコア算出理由（ai_score_reason）も、この9観点に沿った内容が出力されることを期待する。

### 2.5 注記

* 本章の入力要素は「**AI 総合判定によるマッチング**」および「**AI による人材プロフィール要約生成**」の入力パラメータに限定する。営業担当の閲覧用メタ項目（特記事項・顧客名・案件名・面談回数・稼働環境・精算幅・路線情報等）は AI 入力対象外（DB には保持するが AI には渡さない）。
* 各テーブル定義・カラム型・NULL ポリシー・列挙値は **データモデル・DB設計書 v1.7（岡氏）に従う**。本設計書では論理的なマッチング対象として再整理しているのみで、物理設計の決定権は DB設計書側にある。
* スキル入力（engineer_skills / project_skills）はフリーテキスト方式（QA#11・WF_04/WF_07 v2.0 確定）。マスタ管理は廃止。
* 路線情報（engineers.nearest_line / projects.work_location_line）は DB にカラムとして保持されるが AI マッチング対象外。
* 顔写真（QA#46）、所属区分（QA#60）、通勤許容時間（QA#61）、職務経歴書ファイル（WF_04 v2.0 / QA#13・QA#85 の 5/6 打ち合わせで廃止確定）はカラムとして持たない。
* **ソフトスキル・人物要件**（マネジメント経験・上流工程経験・議事録作成経験・顧客折衝経験等）は専用フィールドを設けず、アピールポイント（H1）または人材スキル（H15）にフリーテキストで記述する運用とする。QA#87 は顧客回答の明示記録なきも、**岡氏 DB設計書 v1.7 の内容（専用カラム未設置・engineer_skills のフリーテキスト統合・has_negotiation_exp の独立 BOOL カラム）に準拠する形で暫定的に決定**。旧 S8「顧客折衝/人物要件一致」のルールベース判定は廃止し、AI 総合判定に統合する。

## 03_第3章_スコアリング仕様

100点満点・**AI 総合判定**方式。Bedrock (Claude 3.5 Sonnet) が入力パラメータ全体を理解した上で総合スコアを算出する。

### 3.1 スコアリング方式

**v0.3 までのルールベース（F1ハードフィルタ + S1〜S8配点）を全廃**。直近MTG決定（2026年5月）に基づき、以下の方式に変更：

| 項目 | 内容 |
| :--- | :--- |
| **判定エンジン** | AI（Bedrock Claude 3.5 Sonnet） |
| **配点方式** | 100点満点・AI による総合判定 |
| **ハードフィルタ** | なし（必須スキル不足はAIが低スコア化で表現） |
| **判定の透明性** | AI スコア算出理由（`ai_score_reason` TEXT）で担保 |
| **配点内訳** | なし（旧 S1〜S8 のような数値分解は行わない） |

> **v0.3 からの変更点**：
> - F1（必須スキル全保有チェック）→ 廃止。必須スキルの不足は AI がスコアと算出理由で表現する。
> - S1〜S8 の配点（30/20/10/10/10/10/5/5）→ 廃止。AI が全体を見て 0〜100点で総合判定する。
> - QA#31（5/6 打ち合わせ追記）では「一部ルールベース + 残りAI加算」のハイブリッド方式も顧客許容内だが、本設計では実装の単純化・整合性確保の観点から **完全AI総合判定一本**を採用する。
> - QA#31（配点比率の現場確認中）→ 配点方式自体が廃止されたため事実上クローズ。

---

### 3.2 出力構造（5点セット）

AI は 1回の呼び出しで以下の5項目を JSON 構造化出力する。出力先カラムは DB設計書 v1.7 §4 pipelines テーブル参照。

| # | 項目名 | 出力先カラム | 型 | 内容 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | マッチングスコア | pipelines.match_score | TINYINT UNSIGNED (0〜100) | AI による総合判定値 |
| 2 | マッチングランク | pipelines.match_rank | CHAR(1) | A / B / C / D（§3.3 参照、score から閾値判定） |
| 3 | AIスコア算出理由 | pipelines.ai_score_reason | TEXT | スコアの根拠説明（数百字程度） |
| 4 | AI推薦コメント | pipelines.ai_comment | TEXT | 推薦理由の自然文（200字前後） |
| 5 | 不足条件 | pipelines.ai_missing | TEXT | 満たしていない要件の説明（100字前後） |

> **保存タイミング**：5点セットはマッチング実行のたびに AI がリアルタイム生成する。マッチング結果からパイプラインへ追加した時点で `pipelines` テーブルにスナップショットとして保存される（QA#45 オンデマンド計算・DB保存なし方針との整合）。

> **JSON 構造化出力の理由**：5項目はいずれも「同じマッチング判断の異なる側面」であり、別々のAI呼び出しで生成すると整合性が崩れる（例：score=80 なのに ai_score_reason に「経験不足」と書かれる等）。1回呼び出しで JSON 構造化出力することで、整合性・コスト・速度（QA#30 同期5〜10秒制約）の3点を担保する。プロンプト詳細は **AIプロンプト設計書** を参照。

---

### 3.3 ランク判定

`match_score` から `match_rank` への閾値判定。アプリ層で実施（Python or Laravel どちらでも可）。

| ランク | スコア帯 | 位置付け | UI挙動 |
| :---: | :--- | :--- | :--- |
| **A** | 80〜100点 | 即提案レベル | 通常表示。パイプライン追加推奨 |
| **B** | 65〜79点 | 検討可能 | 通常表示 |
| **C** | 50〜64点 | 条件交渉次第 | 通常表示 |
| **D** | 0〜49点 | 見送り推奨 | opacity（不透明度）低めで表示 |

### 3.4 計算フロー

| Step | 内容 |
| :--- | :--- |
| Step 1 | Laravel から `POST /api/v1/matching/calculate` を実行（パラメータ送信） |
| Step 2 | Python が RDS から人材情報（engineers + engineer_skills）・案件情報（projects + project_skills）を取得 |
| Step 3 | 候補案件群（QA#79 で `status='open'` の案件、または `project_ids` 指定時はその部分集合）を抽出 |
| Step 4 | 候補各案件に対し AI を呼出し、JSON 構造化出力で5点セット（score / rank / score_reason / ai_comment / ai_missing）を取得 |
| Step 5 | スコア降順でソート。上位5件で打ち切り（QA#33・QA#50） |
| Step 6 | 5件分の結果を JSON で Laravel に返却 |
| Step 7 | ユーザーがマッチング結果からパイプライン追加した時点で、Laravel が pipelines テーブルにスナップショット保存 |

> **AI 呼び出し回数**：候補案件数だけ AI を呼び出す。例えば人材1名 × `status='open'` の案件50件 → AI 呼び出し50回。並列実行とBedrockクォータの制御は §5.2 参照。
>
> **絞り込み**：マッチング判定の前段で、`engineers.status='proposable'` および `projects.status='open'` で API 呼び出し側（Laravel）が絞り込み済みであることを前提とする。

### 5.5 LLMプロバイダ選定根拠（Bedrock採用理由）

本設計書は AWS Bedrock / Claude 3.5 Sonnet を前提とする。OpenAI API 等の外部LLMではなく Bedrock を採用する根拠を以下に整理する。

| 観点 | Bedrock Claude 3.5 Sonnet （採用） | OpenAI API （比較） | 決め手 / 関連QA |
| :--- | :--- | :--- | :--- |
| **データガバナンス** | VPCエンドポイント経由でAWS網内完結。個人情報が外部ネットに出ない。顧客データのモデル学習非利用がデフォルト契約。 | 外部egressが発生（米国リージョン経由など）。DPIA／契約上のオプトアウト対応が別途必要。 | QA#25 個人情報保護 |
| **インフラ統一** | ECS/RDS と同一AWS。IAMロールで認証完結、APIキー発行・ローテ不要。 | OpenAI APIキーの発行・Secrets Manager格納・定期ローテが必要。AWS外契約で別請求。 | 運用負荷・漏洩リスク |
| **プロバイダ依存回避** | 同一SDK(boto3 bedrock-runtime)で Claude/Llama/Titan/Mistral等を切替可能。差替はmodel_id変更のみ。 | OpenAI SDK／エンドポイントに固定。乗換時はクライアント層ごと再実装。 | QA#29 プロバイダ依存回避要望 |
