# バリデーション・エラー表示設計書

> 最終更新：2026-05-27

## 概要
- 本ドキュメントは全機能共通のバリデーションおよびエラー表示仕様を定義する
- バリデーションは Laravel（FormRequest）で実装する
- エラーは Inertia.js を通じて Props としてフロントへ渡す

---

## 共通仕様

### 必須/任意の制御方針（重要）
- WF上の「必須」バッジは初期設定値を表すものであり、常に必須であることを意味しない。
- 必須/任意の制御は以下の2層で行う。

**第1層：システム固定必須（DBレベルでNOT NULL）**
- 管理者も変更不可。バリデーションルールに `required` をハードコードする。

| 対象フォーム | フィールド |
|-------------|-----------|
| 人材登録・編集 | `name`（氏名）/ `name_kana` / `status` / `main_user_id` |
| 案件登録・編集 | `name`（案件名）/ `status` / `main_user_id` |

**第2層：動的必須（form_field_settings テーブルで制御）**
- 第1層以外のすべてのフィールドが対象。
- 管理者がマスタ管理画面から必須/任意をトグルで変更可能（QA #65確定）。
- バリデーションルールは FormRequest 内で form_field_settings を参照して動的に組み立てる。
- WF上で「必須」バッジが表示されているフィールドであっても、第2層に該当する場合は `required` をハードコードしてはならない。
- **`※動的` フィールドは任意設定時に `nullable` を付与する**。ENUM型も例外なく `nullable / in:...` の組み合わせで定義すること。

> **根拠：** DB設計書 §1-2 / QA #65・#82確定

### FormRequest 実装方針（参考）

```php
// app/Http/Requests/EngineerRequest.php
public function rules(): array
{
    // 第1層：システム固定必須（ハードコード）
    $rules = [
        'name'         => ['required', 'string', 'max:100'],
        'name_kana'    => ['required', 'string', 'regex:/^[ァ-ヶー　]+$/u'],
        'status'       => ['required', 'in:proposable,interviewing,not_proposable'],
        'main_user_id' => ['required', 'exists:users,id'],
    ];

    // 第2層：form_field_settings を参照して動的に組み立て
    // field_key は form_field_settings テーブルの field_key カラムと1対1で対応する
    $dynamicFields = [
        'birth_date'          => ['date'],
        'nearest_station'     => ['string', 'max:100'],
        'nearest_line'        => ['string', 'max:100'],
        'available_from'      => ['date'],
        'has_negotiation_exp' => ['boolean'],
        'appeal_note'         => ['string', 'max:4000'],
        'desired_rate'        => ['integer', 'min:0'],
        'work_styles'         => ['array'],
        'remarks'             => ['string', 'max:1000']
    ];

    foreach ($dynamicFields as $field => $fieldRules) {
        $isRequired = FormFieldSetting::isRequired('engineer', $field);
        $rules[$field] = array_merge(
            [$isRequired ? 'required' : 'nullable'],
            $fieldRules
        );
    }

    // 工程経験：proc_experience の1設定で proc_* 6フィールドをまとめて制御する
    // WF_12のフォーム設定タブでも「経験工程」として1つのトグルで管理する
    $procRequired = FormFieldSetting::isRequired('engineer', 'proc_experience');
    $procFields = [
        'proc_requirements', 'proc_basic_design', 'proc_detail_design',
        'proc_development',  'proc_testing',       'proc_maintenance',
    ];
    foreach ($procFields as $field) {
        $rules[$field] = [$procRequired ? 'required' : 'nullable', 'boolean'];
    }

    return $rules;
}
```

### 削除済みリソースを操作したときの共通挙動（stale / 404）

> **【2026-08-13 確定】削除済みリソースへの操作で発生する 404 は、Inertia 経由に限り「一覧へ戻す＋フラッシュ」に差し替える。**
> **背景：** 詳細ページをブラウザバックで再表示すると、Inertia の履歴キャッシュにより削除済みレコードが画面に残る。そこから削除・編集を行うとルートモデルバインディングで 404 となり、技術的なエラー画面（開発時はスタックトレース、本番相当では素の 404 ページ）がそのまま表示されていた。編集画面を開いている間に別ユーザーがそのレコードを削除した場合（並行削除）の保存でも同じ 404 が起きる。
> **理由：** 「実在しないリソースに 404 を返す」こと自体は正しく、`destroy` をべき等化して 200 を返す案は仕様・既存テストと衝突するため採らない。変更するのは *見せ方* に限定し、ユーザーに落ち度のない状況を技術的エラーとして見せないようにする。

#### 差し替えの条件

以下を **すべて** 満たす場合のみ、404 応答をリダイレクトに差し替える。1 つでも欠ければ従来どおりの 404 を返す。

| 条件 | 目的 |
|---|---|
| Inertia リクエストである（`X-Inertia` ヘッダーあり） | API 呼び出し・CSV ダウンロード等、画面遷移を伴わない相手には従来どおり 404 を返す |
| ルートモデルバインディング由来の 404 である（`ModelNotFoundException` が原因） | 未定義 URL・意図的な `abort(404)` は対象外 |
| 対象モデルが下表にある | ホワイトリスト方式。モデル追加時に意図せず 404 が握りつぶされることを防ぐ |
| 戻り先を開ける権限がある | 管理者専用画面へ権限のないユーザーを送らない |

#### 戻り先とメッセージ

| モデル | 戻り先 | メッセージ |
|---|---|---|
| Project | `/projects` | 対象の案件が見つかりません。既に削除された可能性があります。 |
| Engineer | `/engineers` | 対象の人材が見つかりません。既に削除された可能性があります。 |
| Pipeline | `/pipelines` | 対象のパイプラインが見つかりません。既に削除された可能性があります。 |
| User（マスタ管理） | `/master`（管理者のみ） | 対象のユーザーが見つかりません。既に削除された可能性があります。 |
| SavedSearch | 操作元の画面へ戻る（取得できない場合は `/dashboard`） | 対象の検索条件が見つかりません。既に削除された可能性があります。 |

- メッセージは `flash.error` としてリダイレクト先へ渡し、`AuthenticatedLayout` のトーストで表示する（フォームのフィールドエラーとは別経路）。
- **【2026-08-16 修正】「削除された」と断定しない文言にする。** この経路は stale ページからの操作だけでなく、最初から存在しない ID（打ち間違い・古い共有 URL）でも通る。ハード削除のため「かつて存在したか」はサーバーからも判別できない。事実（見つからない）を述べ、原因は可能性として添える（共通エラーページの「対象が見つかりません」と同じ語彙に揃える）。
- `PUT` / `PATCH` / `DELETE` に対しては **303 See Other** で返す（302 ではリダイレクト先へ元のメソッドが引き継がれ、Inertia が追従できないため）。
- 実装は例外ハンドラに集約する（`bootstrap/app.php` → `App\Exceptions\StaleResourceRedirector`）。画面ごと・ボタンごとの `onError` では対応できない（`onError` は 422 でのみ発火し、404 を捕捉しないため）。

### 楽観ロック競合時の共通挙動（version 不一致・issue #45）

> **背景：** 人材・案件・パイプライン・ユーザーの編集画面（進捗管理はドロワー、マスタ管理はモーダル）は「読み込み → 編集 → 保存」の間に時間差がある。同じレコードを複数ユーザーが同時に開いて保存すると、後から保存した側が先の更新に気づかないまま無条件に上書きしてしまう（ロストアップデート）。
> **対策：** 対象4テーブル（engineers / projects / pipelines / users）に `version` カラム（DB設計書 §4）を持たせる。編集画面は読み込み時の `version` を保持し、保存リクエストに含めて送信する。サーバー側は保存直前に対象行をロック（`lockForUpdate()`）した上で、送信された `version` と DB上の現在値を照合し、一致する場合のみ更新して `version` を +1 する。前節（削除済み / stale）が「消えたレコードへの操作」を扱うのに対し、本節は「生きているが古い状態のまま保存しようとした操作」を扱う。

#### バリデーション

`version` は対象4エンドポイントの更新リクエストでのみ `required / integer / min:0` とする。新規作成（POST）には version の概念がないため対象外。

| エンドポイント | version |
|---|---|
| `PUT /engineers/{id}` | 必須（`POST /engineers` は対象外） |
| `PUT /projects/{id}` | 必須（`POST /projects` は対象外） |
| `PATCH /pipelines/{id}` | 必須（他フィールドは部分更新のため nullable だが version のみ必須） |
| `PUT /master/users/{id}` | 必須（`POST /master/users` は対象外） |

#### 不一致時の挙動

| モデル | 戻り先 | メッセージ |
|---|---|---|
| Engineer | 編集画面（`back()`） | 他のユーザーがこの人材情報を更新しました。最新のデータを表示しました。 |
| Project | 編集画面（`back()`） | 他のユーザーがこの案件情報を更新しました。最新のデータを表示しました。 |
| Pipeline | 進捗管理（`back()`。referer が無い場合は `/pipelines`） | 他のユーザーがこのパイプラインを更新しました。最新のデータを表示しました。 |
| User（マスタ管理） | `/master`（`back()`。referer が無い場合は `/master`） | 他のユーザーがこのユーザー情報を更新しました。最新のデータを表示しました。 |

- メッセージは `flash.error` としてリダイレクト先へ渡し、`AuthenticatedLayout` のトーストで表示する（削除済みリソースの stale/404 と同じ経路）。
- `back()` で戻る画面は、保存を試みた時点のDBの最新データを改めて取得して表示する（＝競合させた相手の更新内容が見える）ため、追加の再読み込み操作は不要。
- 実装は `App\Exceptions\StaleUpdateException` を各 Service 層（`EngineerService` / `ProjectService` / `PipelineService` / `UserService`）が投げ、各 Controller の `update()` が個別に捕捉して上記メッセージを返す。前節（stale/404）が例外ハンドラへ集約しているのに対し、こちらは集約しない：バージョン照合は「同じレコードの更新」という業務ロジック本体の一部であり、複数モデルにまたがる横断的な404の握りつぶしとは性質が異なるため。
- 一覧・詳細取得（GET）では `version` を常に Resource の一部として返す（各章「送信データ」節参照）。

> **【2026-09-01 追記】CSVインポート（人材・案件の更新行）も同じ `version` に相乗りする（issue #45 スコープ追加）**
> 対象は `engineers` / `projects` のみ（`pipelines` / `users` にはCSV入出力機能自体が無い）。挙動は本節の4画面（1レコードずつの `PUT`/`PATCH` → `back()` リダイレクト＋トースト）とは形が異なる：CSVインポートは複数行を1リクエストでバッチ処理するため、`version` 不一致は他の項目バリデーションと同じ **422 のエラー行一覧**（`row`/`field: "version"`/`messages`）の1エントリとして返り、**全行ロールバック方針**に従う（1行でも不一致があれば他の正常行も含め書き込まれない）。エクスポートに参照用の `バージョン（システム管理）` 列を追加し（列名にシステム管理である旨を明記し業務項目と区別している）、更新行（`id` 指定）は必須・照合必須、新規行（`id` 空）は無視して常に `0` とする。詳細は `api/08_CSV入出力_APIエンドポイント一覧.md`「並行制御（ロストアップデート）について」および本書「8. CSV入出力」を参照。

### エラーページの共通挙動（404 / 403 / 419 / 500 / 503）

> **【2026-08-15 確定】上記の差し替え条件に合致しないエラーは、アプリの体裁を保った共通エラーページ（`Pages/Error.tsx`）で受ける。**
> **背景：** カスタムエラーページが 1 枚も存在せず、フレームワーク既定の応答（開発時はスタックトレース、本番相当では素の白ページ）がそのまま表示されていた。サイドバーもヘッダーも無く、アプリへ戻る導線が無いため、社内ツールでも「システムが壊れた」と受け取られる状態だった。
> **理由：** 前節（stale/404）が「エラーを出さないようにする」対策であるのに対し、本節は「それでも出てしまったときの受け皿」を定める。両者は排他ではなく直列に並ぶ。

#### 差し替えの対象と挙動

| ステータス | 到達経路の例 | 挙動 |
|---|---|---|
| 404（未定義 URL） | URL の打ち間違い・古いブックマーク | 「アクセスしようとしたページが見つかりません」＋ URL 確認を促す案内 |
| 404（対象なし） | 削除済み対象の共有 URL・存在しない ID の直打ち・前節の条件に合致しない 404 | 「対象が見つかりません」＋ 削除済み／URL 誤りの可能性と、一覧の確認を促す案内 |
| 405 | 未定義 URL への POST / DELETE（古いタブからの送信）、定義済み URL へのメソッド違い | 「この操作は実行できませんでした」＋ 開き直しを促す案内 |
| 403 | 一般ユーザーが `/master` を直接開く | 「このページを表示する権限がありません」（連絡先は `admin` ロールのユーザー＝画面上の「管理者」） |
| 419 | CSRF トークン不一致（**同一オリジンのブラウザ操作では発生しない**。下記参照） | **エラーページを出さない。** ログイン済みは元の画面へ戻し `flash.error` をトースト表示、未ログインはログイン画面へ送り `status` を表示 |
| 500 | 想定外の例外 | 「システムエラーが発生しました」。**`APP_DEBUG=true` のときは差し替えずスタックトレースを残す** |
| 503 | メンテナンス | 「ただいまメンテナンス中です」 |

- **HTTP ステータスコードは元の値のまま返す**（404 は 404）。差し替えるのは表示内容だけで、応答の意味は変えない。
- 404 の文言は原因（未定義 URL／対象なし）で出し分ける。サーバー側が入口で区別できるため、`reason`（`missing_page` / `missing_resource`）として渡す。1 つの文言に丸めると、どちらのユーザーにも半分しか当たらない案内になるため。
- 復帰導線は認証状態で変える。認証済みはサイドバー（`AppSidebar`）が導線を兼ねるためページ内にボタンを置かず、未認証は `GuestLayout` にナビゲーションが無いため「ログイン画面へ」のボタンを置く。未認証でも 404 は 404 のまま返し、ログイン画面へリダイレクトしない。
- 500 の文言に問い合わせ窓口は書かない。本アプリの「管理者」は `admin` ロールのユーザーを指し、アプリ障害の窓口ではないため（運用窓口が定義された時点で本節と文言を更新する）。
- スタックトレース・例外クラス名などの技術情報は表示しない。

#### 実装の所在

| 対象 | 実装 |
|---|---|
| ルート内で発生した例外（403 / 404 / 419 / 500 / 503） | `bootstrap/app.php` の `$exceptions->respond()` → `App\Exceptions\ErrorPageResponder` |
| 未定義 URL | `routes/web.php` の `Route::fallback()` → 同上 |
| 画面 | `resources/js/Pages/Error.tsx`（認証状態で `AuthenticatedLayout` / `GuestLayout` を出し分け） |

未定義 URL を例外ハンドラだけで処理すると、`web` ミドルウェアグループ（`StartSession` / `HandleInertiaRequests`）が実行されず**共有 Props が一切載らない**ため、ログイン済みでも未認証向けの表示になる。これを避けるために `Route::fallback()` を併用する。

同様に、`HandleInertiaRequests` は web グループの末尾に置かれており、**ルートモデルバインディング（`SubstituteBindings`）の 404 はそれより前に発生する**。この経路でも共有 Props が未設定になるため、エラーページの描画前に共有状態を確認し、未設定なら `HandleInertiaRequests::share()` を呼んで補う（ミドルウェアの順序自体は変更しない）。**エラーページは「どの画面を出すか」だけでなく「誰として出すか」が崩れやすい**ため、テストでは `auth.user` まで検証すること。

差し替え対象のステータスは許可リスト（`403 / 404 / 405 / 419 / 500 / 503`）で管理する。`respond()` にはすべての例外応答が流れるため、範囲判定にすると前節のリダイレクト（302 / 303）やバリデーションの 422 まで巻き込み、フォームのエラー表示が無言で壊れる。JSON クライアント（`expectsJson()`）にも差し替えを行わない。

`Route::fallback()` は GET / HEAD にしか登録されない（`Illuminate\Routing\Router::fallback`）ため、未定義 URL への POST / DELETE は 404 ではなく **405** になる。405 を許可リストに含めていないと、古いタブからの送信が素のエラー画面に落ちる。

> **【2026-08-24 確定】405 は「誰として出すか」が崩れる（既知の制限として許容する）**
> **背景：** メソッド不一致は**ルート確定より前**に検出される（`RouteCollection::getRouteForMethods`）ため、`web` グループ（`StartSession` / `HandleInertiaRequests`）が一度も実行されない。前段落の補完処理はセッションの存在を前提にしているため働かず、共有 Props は null ですらなく**存在しない**。結果、ログイン中のユーザーが 405 に遭遇してもエラーページは未認証向けの見た目（サイドバー無し・「ログイン画面へ」）になる。
> **理由：** 解消するにはルート未確定の段階でセッションを開始する経路を自前で用意することになり、全リクエストの前提に触れる。得られるのは**低頻度な 405 での見た目の一貫性**だけで、影響範囲に見合わない。ステータス・文言・復帰可能性は正しく保たれるため、表示の不整合として許容する。
> **担保：** 「直っていないこと」ではなく「現状こうであること」を `ErrorPageTest::test_undefined_url_with_post_renders_error_page` の `->missing('auth')` で固定する。将来対応した場合はこのアサーションが落ち、意図的な変更だと分かる。

> **【2026-08-24 修正】案内ページの描画自体が失敗したときの退避先を、両方の入口で定める。**
> **背景：** 案内ページの描画は Vite マニフェストやビューに依存するため、フロント資材とコードがズレた環境（ビルド未実行など）では描画自体が失敗しうる。`respond()` 側にはフェイルセーフがあったが `Route::fallback()` 側には無く、**未定義 URL への 404 だけが素の 500 に格上げ**される状態だった。本クラスが受ける経路の中で未定義 URL は最も頻度が高い（打ち間違い・古いブックマーク・クローラ）。
> **理由：** 描画に失敗しても**応答の意味（ステータス）は保つ**のが本機能の最低ラインである。見た目はフレームワーク既定に劣化してよいが、404 が 500 になると利用者への説明も監視上の意味も変わる。したがって `respond()` は元の応答へ、`Route::fallback()` は退避先の応答を持たないためフレームワーク既定の 404（`NotFoundHttpException` を投げ直す）へ退避する。再投函した例外は再び `respond()` に流れるので、リクエスト属性に失敗の印を残して**同じ描画を二度試さない**。
> **理由（ログ）：** 退避を無言で行うと「案内ページが出せない」という不具合そのものが隠れる（利用者には既定のエラー画面が出るだけ）。両方の退避経路で `report()` して必ずログに残す。

419 でログイン画面へ送ってよいのは未ログインのときだけである。ログイン済み（セッションは生きていてトークンだけ失効）でログイン画面へ送ると、`guest` ミドルウェアがログイン済みを弾いてダッシュボードへ再リダイレクトし、フラッシュが一度も描画されずに消える（送信の失敗すら伝わらない Silent Rejection）。

> **【2026-08-16 確定】419 の到達経路（Laravel 13 での実態）**
> **背景：** 実機検証で、`XSRF-TOKEN` Cookie を破壊しても画面操作が 419 にならないことが判明した。
> **理由：** Laravel 13 の CSRF ミドルウェアは `ValidateCsrfToken` から **`PreventRequestForgery`** に変わり、判定が `isReading()` → **`hasValidOrigin()`** → `tokensMatch()` の順になった（`PreventRequestForgery::handle`）。ブラウザは同一オリジンの XHR に必ず `Sec-Fetch-Site: same-origin` を付けるため、**トークンを検証する前に通過する**。
>
> したがって 419 が実際に発生するのは次の場合に限られる。
> - クロスサイトからの送信でトークンが一致しない
> - `Sec-Fetch-Site` を送らないクライアント（curl・古いブラウザ）でトークンが無い／不一致
>
> **画面操作でのセッション期限切れは 419 にならず、`auth` ミドルウェアによる 302 →ログイン画面**になる。419 の分岐は上記クライアント向けの防御として維持する。
> なお `useOriginOnly()` を有効にした場合のオリジン不一致は `OriginMismatchException` → **403** であり、419 ではない（現在は無効）。

419 の戻り先は **自ホスト内に限定する**こと。`url()->previous()` は `Referer` ヘッダーを最優先で使うため（`UrlGenerator::previous`）、クロスサイトからの送信で発生した 419 でそのまま使うと、攻撃者が指定した外部 URL へのリダイレクトを自ドメインから発行することになる。CSRF 自体はミドルウェアが到達前に拒否しており状態変更は起きないが、オープンリダイレクトの原型を残さない。

エラーページ描画の前には、共有 Props に加えて **Inertia のアセットバージョンも補う**こと。欠けると `version` が空のまま描画され、その画面からの次の Inertia 遷移がバージョン不一致（409）と判定されて毎回フルリロードになる。

#### アプリ層バリデーション（FormRequest 外で実装）

FormRequest のバリデーション通過後、Controller 内で以下を追加チェックする。

**重複チェック**

```php
// (engineer_id, project_id) の組み合わせが pipelines テーブルに存在しないこと
// DB設計書 §5：(engineer_id, project_id) に UNIQUE 制約あり
$exists = Pipeline::where('engineer_id', $request->engineer_id)
                  ->where('project_id', $request->project_id)
                  ->exists();
if ($exists) {
    // 422 を返す
    // メッセージ：「この人材はすでにこの案件のパイプラインに追加されています」
}
```

**上限チェック**

```php
// 同一 project_id の「進行中（アクティブ）」パイプライン件数が5件未満であること（QA #50確定）。
// 終了済み（terminal：不成立・見送り等）は枠を消費しない＝再度追加できる（アクティブ5件で判定）。
$count = Pipeline::where('project_id', $request->project_id)
    ->whereIn('status', Pipeline::inProgressValues())
    ->count();
if ($count >= 5) {
    // 422 を返す
    // メッセージ：「この案件のパイプラインはすでに上限（5件）に達しています」
}
```

> **カウント対象（アクティブ5件）**：上限は「進行中（アクティブ）」のパイプラインのみを数える。
> 終了済みステータス（`Pipeline::terminalValues()`）は枠を消費しないため、ある人材の進捗が終了すると
> 案件のアクティブ枠が空き、**別の（未追加の）人材**を新たに追加できる。マッチング結果画面の
> 「上限到達」先出し無効化（`is_project_full`）も同一基準で判定する。
>
> **上限チェックと重複チェックは別ルール**：上記の重複チェック（`(engineer_id, project_id)` の
> UNIQUE 制約）はステータスに関わらず有効なため、**同一人材を同一案件へ再追加することはできない**
> （その人材のパイプラインが終了済みになっても不可）。アクティブ枠が空くのはあくまで他人材向け。

## 8. CSV入出力

### POST /csv/engineers/import・POST /csv/projects/import（共通）

#### ファイルバリデーション

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|
| file | required / file | CSVファイルを選択してください |
| file | （拡張子チェック `.csv`） | ファイルの拡張子を「.csv」にしてください |
| file | mimes:csv,txt（内容の推測MIME） | ファイル形式が正しくありません。CSVファイル（.csv）をアップロードしてください |
| file | （サイズチェック）max:5120（KB） | ファイルサイズは5MB以内にしてください |

> **評価順（`bail` で最初の失敗のみ返す）：** required → file → **拡張子（.csv）→ 形式（mimes）** → サイズ。「まず .csv という名前か」を先に判定し、拡張子が合っていて中身だけ偽物のケース（例：画像を `.csv` にリネーム）を後段の mimes で弾く。

> **【2026-08-01 修正】ファイル形式エラーのメッセージを拡張子チェックと `mimes`（内容）で2分割した**
> **背景：** 従来はどちらも「.csvファイルを選択してください」で共通化していたが、`mimes:csv,txt` はクライアント拡張子ではなく**ファイル内容から推測した MIME タイプ**を検証しており、拡張子だけを指す文言は実態とズレていた。
> **理由：** 失敗モードが異なる（拡張子チェック＝ファイル名が `.csv` でない例：`.txt`／`mimes`＝拡張子は合っているが中身がCSV/テキストとして認識できない例：xlsx や画像をリネーム）。原因に応じて「拡張子を .csv に」「形式が違う」と案内を分けることで、ユーザーが取るべき対処が明確になる。
>
> **【2026-08-02 修正】チェック順序を「拡張子 → 形式(mimes)」に変更（拡張子を先に評価）**
> **背景：** 実装当初は基本ルールの `mimes`（形式）が先に走り、拡張子チェックは `after()`（基本ルールの後）にあったため、`report.pdf` のように拡張子が明らかに違うファイルでも「形式が正しくありません」と表示され、対処が伝わりにくかった。
> **理由：** 拡張子は最も表層的で分かりやすいゲート。先に判定することで「拡張子が違う＝拡張子を直す」「拡張子は合っているが中身が偽物＝形式が違う」と切り分けが明確になる。設計書のファイルレベル順序「①ファイル（拡張子/サイズ/文字コード）」とも整合する。実装は拡張子チェックを `rules()` へ前出しし `bail` で順に評価する。実装は `App\Http\Requests\Csv\CsvImportRequest`。

> **`mimes:csv,txt` について**：LaravelのMIMEタイプ判定では `text/csv` が `txt` と判定されることがあるため `csv,txt` の両方を許容する。拡張子が `.csv` かどうかは追加チェックを実装すること。  
> **文字コードチェック**：UTF-8（BOMあり・なし）以外の文字コード（Shift-JIS等）は処理前に検出してエラーを返すこと。エラーメッセージ例：「UTF-8形式のCSVファイルをアップロードしてください」
> **行数上限（O-13 確定）**：空行スキップ後の**データ行が 5,000 行を超える場合はエラー**を返す（同期処理のタイムアウト回避。5MB のサイズ上限と併用）。エラーメッセージ例：「一度にインポートできるのは5,000行までです。ファイルを分割してインポートし直してください」。この判定はレイアウト/項目バリデーションより前（ファイルレベル）で行う。

#### CSV仕様・空行・チェック順序（2026-07-30 確定）

- **準拠：RFC 4180**。区切りはカンマ。引用符はダブルクオート `"` で、値が「カンマ・`"`・改行」を含む場合のみ囲みが必須（値中の `"` は `""` エスケープ）。シングルクオート `'` は引用符として扱わない。詳細は `api/08_CSV入出力_APIエンドポイント一覧.md`「ファイル仕様」を参照。RFC4180準拠のパーサ／ライターを用い、`"..."` 内の改行は1論理レコードの一部として扱う（`\n` 単純分割禁止）。
- **空行＝改行だけの行**はスキップし、件数（`total_rows`/`created`/`updated`）・エラーに計上しない。`,,,,` は必須項目エラー、スペースだけの行は下記レイアウトエラーになる（いずれもデータ行扱い）。行番号は元のCSV論理行番号を維持。
- **チェック順序**：①ファイル（拡張子/サイズ/文字コード）→ ②ヘッダー行（不正なら全体中断）→ ③行レイアウト（列数一致。不一致は `field:null` の構造エラー）→ ④項目バリデーション（下記）。**レイアウトを項目より先**に行い、列数が不正な行は項目バリデーションをスキップする。

---

#### 行バリデーション（人材インポート）

CSVの各行に対してバリデーションを適用する。1行でもエラーがある場合は全行ロールバックし、エラー内容を返す。

> **フォームとの整合（O-5 / 2026-07-31 確定）**：CSVインポートの**各項目の書式・範囲ルール（max/min/date/regex/in/boolean/gte・lte/different 等）は、人材登録 `EngineerRequest` ／案件登録 `ProjectRequest` と一致**させる（例：`desired_rate` max:999、`headcount` max:99、`interview_count` max:10、単価 max:999、`birth_date` before_or_equal:today、`appeal_note` max:4000、`remarks`(人材) max:1000）。ただし**必須/任意の判定だけはCSV独自**（`form_field_settings` 非適用。固定必須は人材＝`name`/`name_kana`/`status`/`main_user_id`、案件＝`name`/`status`/`main_user_id`）。実装ではフォームとCSVで**ルール定義を共有／単一の出所**にし、フォーム側の変更がCSVにも波及するようにすることが望ましい（DRY）。
> **2点の確定（2026-07-31）**：(1) 案件 `work_location_station` は**フォーム同様の業務ルール `required_if:work_style,onsite,hybrid` を CSV でも適用**する（`form_field_settings` とは別の固定業務ルール。常駐・一部リモート可の行は最寄駅必須）。(2) 0/1 フラグ列（`work_style_onsite/hybrid/remote`・各 `proc_*`・`has_negotiation_exp`・`negotiation_required`）は**CSV では `in:0,1` に限定**する（フォームの `boolean` と異なり `true/false` は受理しない。CSVは 0/1 に統一して明快にするため）。
> **エラーの粒度（2026-07-30 確定）**：1項目（=1セル）につき、失敗したバリデーションを**すべて**返す（`bail` は使わない）。例：`name_kana` が「漢字（regex 違反）」かつ「100文字超（max 違反）」の場合、「カナで入力してください」「100文字以内で入力してください」の**両方**を返す。レスポンスは同一 (row, field) を1エントリにまとめ `messages: string[]` で列挙する（区切り文字での連結はしない）。行構造の崩れ（列数不一致など）は `field: null` の1エントリで返す。詳細は `api/08_CSV入出力_APIエンドポイント一覧.md` を参照。  
> **CSVインポートと `form_field_settings` の関係**：フォーム画面の必須/任意制御（form_field_settings）はCSVインポートに適用しない。CSVは `name` / `name_kana` / `status` / `main_user_id` のみ必須とし、それ以外はNULL許容とする（DB設計書 §1-2準拠）。  
> **空セルの扱い**：空セルは `null` として処理し、既存データをNULLで上書きする（空文字とnullは同一扱い）。  
> **`name` / `name_kana` の正規化**：フォーム登録と同様に、インポート時も**半角スペースを全角スペースへ変換**してからバリデーションを適用すること。人材は `name` と `name_kana` の両方を対象とする（`name` の正規化は PR #21 レビュー指摘対応。`EngineerRequest::prepareForValidation()` と挙動を揃える）。案件 `name` は `ProjectRequest` が正規化しないため CSV でも正規化しない。
> **担当者名列（`主担当名` / `サブ担当名`）**：エクスポート専用の参照列。**インポート時は読み飛ばし、バリデーションも適用しない**（担当者の紐付けは `主担当ID` / `サブ担当ID` を正とする）。`ai_summary` と同じ扱い。詳細は `api/08_CSV入出力_APIエンドポイント一覧.md` §3 参照。

#### 行バリデーション（案件インポート）

> **CSVインポートと `form_field_settings` の関係**：フォーム画面の必須/任意制御（form_field_settings）はCSVインポートに適用しない。CSVは `name` / `status` / `main_user_id` のみ必須とし、それ以外はNULL許容とする（DB設計書 §1-2準拠）。

### PUT /master/users/{id}（ユーザー編集）

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|
| name | required / string / max:100 | 氏名は必須です |
| email | required / string / email / max:255 / unique:users,email,{id} / ends_with:（社内ドメイン） | 有効なメールアドレスを入力してください / このメールアドレスはすでに使用されています / 社内メールアドレスを入力してください |
| password | nullable / string / min:8 / confirmed | パスワードは8文字以上で入力してください / パスワードが一致しません |
| password_confirmation | required_with:password / string | パスワード（確認）を入力してください |

| version【issue #45 追加】 | required / integer / min:0 | - |

> **`unique:users,email,{id}` について**：自分自身のメールアドレスはユニーク制約の対象外にするため、除外IDを指定する（Laravel標準の `unique` ルール）。  
> **`password` が任意である理由**：編集時にパスワードを変更しない場合は省略可能。省略時はパスワード変更なし。パスワードリセット（管理者による再設定）もこのエンドポイントで対応する（QA #20確定）。

### DELETE /master/users/{id}（ユーザー削除）

バリデーションパラメータなし。アプリ層で以下を実装する。

```php
// 自分自身への削除を防ぐ（TBD#2）
if ($user->id === auth()->id()) {
    // 422：自分自身のアカウントは削除できません
}

// 担当中の人材・案件件数チェック（DB設計書 §7確定）
$engineerCount = Engineer::where('main_user_id', $user->id)->count();
$projectCount  = Project::where('main_user_id', $user->id)->count();

if ($engineerCount > 0 || $projectCount > 0) {
    // 422：担当中の案件が{$projectCount}件、人材が{$engineerCount}件あるため
    //       削除できません。一覧画面から別の担当者へ変更してから再度実行してください。
}
```

### PUT /master/form-settings（フォーム設定更新）

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|
| settings | required / array / min:1 | - |
| settings.*.form_type | required / in:engineer,project | 不正なフォーム種別です |
| settings.*.field_key | required / string / exists:form_field_settings,field_key | 存在しないフィールドキーです |
| settings.*.is_required | required / boolean | 不正な値です |

> **システム固定必須フィールドへの変更ガード（アプリ層）**

```php
foreach ($request->settings as $setting) {
    $record = FormFieldSetting::where('form_type', $setting['form_type'])
                              ->where('field_key', $setting['field_key'])
                              ->first();
    // is_system_required = true のフィールドは変更をスキップ
    if ($record && $record->is_system_required) {
        continue;
    }
    $record->update([
        'is_required' => $setting['is_required'],
        'updated_by'  => auth()->id(),
    ]);
}
```
