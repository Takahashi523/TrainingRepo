# バリデーション・エラー表示設計書

> 最終更新：2026-05-27

## 概要
- 本ドキュメントは全機能共通のバリデーションおよびエラー表示仕様を定義する
- バリデーションは Laravel（FormRequest）で実装する
- エラーは Inertia.js を通じて Props としてフロントへ渡す

---

## 共通仕様

### 必須/任意の制御方針（重要）
- WF上の「必須」バッジは初期設定値を表すものであり、常に必須であることを意味しない。
- 必須/任意の制御は以下の2層で行う。

**第1層：システム固定必須（DBレベルでNOT NULL）**
- 管理者も変更不可。バリデーションルールに `required` をハードコードする。

| 対象フォーム | フィールド |
|-------------|-----------|
| 人材登録・編集 | `name`（氏名）/ `name_kana` / `status` / `main_user_id` |
| 案件登録・編集 | `name`（案件名）/ `status` / `main_user_id` |

**第2層：動的必須（form_field_settings テーブルで制御）**
- 第1層以外のすべてのフィールドが対象。
- 管理者がマスタ管理画面から必須/任意をトグルで変更可能（QA #65確定）。
- バリデーションルールは FormRequest 内で form_field_settings を参照して動的に組み立てる。
- WF上で「必須」バッジが表示されているフィールドであっても、第2層に該当する場合は `required` をハードコードしてはならない。
- **`※動的` フィールドは任意設定時に `nullable` を付与する**。ENUM型も例外なく `nullable / in:...` の組み合わせで定義すること。

> **根拠：** DB設計書 §1-2 / QA #65・#82確定

### FormRequest 実装方針（参考）

```php
// app/Http/Requests/EngineerRequest.php
public function rules(): array
{
    // 第1層：システム固定必須（ハードコード）
    $rules = [
        'name'         => ['required', 'string', 'max:100'],
        'name_kana'    => ['required', 'string', 'regex:/^[ァ-ヶー　]+$/u'],
        'status'       => ['required', 'in:proposable,interviewing,not_proposable'],
        'main_user_id' => ['required', 'exists:users,id'],
    ];

    // 第2層：form_field_settings を参照して動的に組み立て
    // field_key は form_field_settings テーブルの field_key カラムと1対1で対応する
    $dynamicFields = [
        'birth_date'          => ['date'],
        'nearest_station'     => ['string', 'max:100'],
        'nearest_line'        => ['string', 'max:100'],
        'available_from'      => ['date'],
        'has_negotiation_exp' => ['boolean'],
        'appeal_note'         => ['string', 'max:4000'],
        'desired_rate'        => ['integer', 'min:0'],
        'work_styles'         => ['array'],
        'remarks'             => ['string', 'max:1000']
    ];

    foreach ($dynamicFields as $field => $fieldRules) {
        $isRequired = FormFieldSetting::isRequired('engineer', $field);
        $rules[$field] = array_merge(
            [$isRequired ? 'required' : 'nullable'],
            $fieldRules
        );
    }

    // 工程経験：proc_experience の1設定で proc_* 6フィールドをまとめて制御する
    // WF_12のフォーム設定タブでも「経験工程」として1つのトグルで管理する
    $procRequired = FormFieldSetting::isRequired('engineer', 'proc_experience');
    $procFields = [
        'proc_requirements', 'proc_basic_design', 'proc_detail_design',
        'proc_development',  'proc_testing',       'proc_maintenance',
    ];
    foreach ($procFields as $field) {
        $rules[$field] = [$procRequired ? 'required' : 'nullable', 'boolean'];
    }

    return $rules;
}
```

### エラー構造（Inertia）
```
errors.name
errors.skills.0.label
errors.skills.0.detail
errors.proc_requirements
errors.main_user_id
```

### Props構造
| フィールド | 型 | 説明 |
|-----------|----|----|
| errors | object | バリデーションエラー |
| errors.{field} | string | 先頭のエラーメッセージ |

### エラー表示ルール（UI）
| 項目 | 内容 |
|------|------|
| 表示位置 | 入力項目の直下 |
| 表示件数 | 各フィールドごとに先頭1件を表示 |
| 表示タイミング | submit後 |
| スクロール | 最初のエラーへスクロール |
| 表示形式 | 赤文字表示 |

### エラーメッセージ方針
- 日本語で表示する
- 項目名＋エラー内容の形式とする
- 丁寧語で統一する（〜してください）
- フィールド単位でエラーを表示する
- エラーメッセージはLaravelのlangファイルで管理する

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|

### バリデーション定義

> ※ 「※動的」のフィールドは form_field_settings テーブルを参照して必須/任意を制御する（第2層）。  
> ※ 「※動的」フィールドは任意設定時に `nullable` を付与する。ENUM型も `nullable / in:...` の組み合わせとする。  
> ※ `fieldSettings` の各キーは form_field_settings テーブルの `field_key` カラムと1対1で対応する。  
> システム固定必須（DBレベルで NOT NULL）は `name` / `name_kana` / `status` / `main_user_id` のみ。それ以外のフィールドはDBレベルではNULL許容とする。

#### 基本情報

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|
| name | required / string / max:100 | 氏名は必須です |
| name_kana | required / string / regex:/^[ァ-ヶー　]+$/u | カナで入力してください |
| birth_date | ※動的 / date | 正しい日付を入力してください |
| nearest_station | ※動的 / string / max:100 | 最寄駅は100文字以内で入力してください |
| nearest_line | ※動的 / string / max:100 | 路線名は100文字以内で入力してください |
| available_from | ※動的 / date | 稼働可能日を入力してください |

> `name_kana` の入力正規化：バリデーション前に半角スペースを全角スペースへ変換する
> （FormRequest の `prepareForValidation()` で実装）。
> ユーザーは半角・全角どちらでも入力可能。DBには全角スペースで統一して保存する。

#### スキル情報

> **skills の件数バリデーションについて：**
> skills の必須/任意は form_field_settings で制御する（DB設計書 §1-2）。
> - form_field_settings で skills が必須の場合：空配列・省略ともにエラー
> - form_field_settings で skills が任意の場合：空配列・省略ともに許容（全削除として扱う）
> - PUT時に skills: [] を送信した場合、既存スキルを全件削除する
> - PUT時に skills キーを省略した場合も同様に全件削除として扱う

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|
| skills | nullable / array | - |
| skills.*.label | required_with:skills.*.detail / string / max:15 | スキル名は15文字以内で入力してください。detail入力時はlabelも必須 |
| skills.*.detail | nullable / string / max:500 | スキル詳細は500文字以内で入力してください |
| proc_requirements | ※動的 / boolean | 不正な値です |
| proc_basic_design | ※動的 / boolean | 不正な値です |
| proc_detail_design | ※動的 / boolean | 不正な値です |
| proc_development | ※動的 / boolean | 不正な値です |
| proc_testing | ※動的 / boolean | 不正な値です |
| proc_maintenance | ※動的 / boolean | 不正な値です |
| has_negotiation_exp | ※動的 / boolean | 選択してください |

> **工程経験（proc_*）の動的制御について：**
> proc_* 6フィールドの必須/任意は `form_field_settings` の `field_key = "proc_experience"` の1設定でまとめて制御する。
> WF_12のフォーム設定タブでも「経験工程」として1つのトグルで管理する。

| rate_max | ※動的 / integer / min:0 / gte:rate_min | 正しい金額を入力してください |

> ※ `work_location_station` の条件付き必須は `form_field_settings` の動的制御ではなく、業務ルールによる固定の条件付き必須とする。

### POST /pipelines（マッチング画面からの追加）

#### フィールドバリデーション

| フィールド | バリデーション | エラーメッセージ例 |
|-----------|-------------|----------------|
| engineer_id | required / integer / exists:engineers,id | 対象人材が存在しません |
| project_id | required / integer / exists:projects,id | 対象案件が存在しません |
| match_score | required / integer / min:0 / max:100 | 不正なスコア値です |
| match_rank | required / in:A,B,C,D | 不正なランク値です |
| ai_score_reason | nullable / string | - |
| ai_comment | nullable / string | - |
| ai_missing | nullable / string | - |

#### アプリ層バリデーション（FormRequest 外で実装）

FormRequest のバリデーション通過後、Controller 内で以下を追加チェックする。

**重複チェック**

```php
// (engineer_id, project_id) の組み合わせが pipelines テーブルに存在しないこと
// DB設計書 §5：(engineer_id, project_id) に UNIQUE 制約あり
$exists = Pipeline::where('engineer_id', $request->engineer_id)
                  ->where('project_id', $request->project_id)
                  ->exists();
if ($exists) {
    // 422 を返す
    // メッセージ：「この人材はすでにこの案件のパイプラインに追加されています」
}
```

**上限チェック**

```php
// 同一 project_id の「進行中（アクティブ）」パイプライン件数が5件未満であること（QA #50確定）。
// 終了済み（terminal：不成立・見送り等）は枠を消費しない＝再度追加できる（アクティブ5件で判定）。
$count = Pipeline::where('project_id', $request->project_id)
    ->whereIn('status', Pipeline::inProgressValues())
    ->count();
if ($count >= 5) {
    // 422 を返す
    // メッセージ：「この案件のパイプラインはすでに上限（5件）に達しています」
}
```

> **カウント対象（アクティブ5件）**：上限は「進行中（アクティブ）」のパイプラインのみを数える。
> 終了済みステータス（`Pipeline::terminalValues()`）は枠を消費しないため、ある人材の進捗が終了すると
> 案件のアクティブ枠が空き、**別の（未追加の）人材**を新たに追加できる。マッチング結果画面の
> 「上限到達」先出し無効化（`is_project_full`）も同一基準で判定する。
>
> **上限チェックと重複チェックは別ルール**：上記の重複チェック（`(engineer_id, project_id)` の
> UNIQUE 制約）はステータスに関わらず有効なため、**同一人材を同一案件へ再追加することはできない**
> （その人材のパイプラインが終了済みになっても不可）。アクティブ枠が空くのはあくまで他人材向け。

**Controller 内での固定値セット**

```php
Pipeline::create([
    'engineer_id'     => $request->engineer_id,
    'project_id'      => $request->project_id,
    'status'          => 'proposed',            // 初期ステータス固定（QA #49確定）
    'match_score'     => $request->match_score,
    'match_rank'      => $request->match_rank,
    'ai_score_reason' => $request->ai_score_reason,
    'ai_comment'      => $request->ai_comment,
    'ai_missing'      => $request->ai_missing,
    // client_comment / ng_reason / next_action_date は初期値 null
]);
```
